## กอง ข. งานที่ต้องทำในระบบ

### B0 — ⚠ ช่องโหว่ที่เจอระหว่างวางแผน B2 (ไม่ใช่ฟีเจอร์ ต้องทำก่อน)

**ผู้ใช้ระดับ `member` น่าจะเลื่อนตัวเองเป็น `admin` ได้ ด้วยคำขอ HTTP เดียว**

migration 003 สร้าง policy นี้:

```sql
create policy "update own profile" on profiles
  for update using (id = auth.uid()) with check (id = auth.uid());
```

คอมเมนต์ในไฟล์เขียนว่า *"Role changes are still restricted: this policy only permits
a user to edit their OWN row"* — ประโยคนี้ถูกครึ่งเดียว มันห้ามแก้ **แถวของคนอื่น**
ได้จริง แต่**ไม่ได้ห้ามแก้คอลัมน์ `role` ในแถวของตัวเอง** เพราะทั้ง `using` และ
`with check` ตรวจแค่ว่าเป็นแถวของตัวเองหรือไม่ ไม่ได้ตรวจว่าแก้คอลัมน์ไหน

คีย์ anon เป็นค่าสาธารณะ (อยู่ใน bundle ของเบราว์เซอร์) ผู้ใช้ที่ล็อกอินแล้วจึงยิงคำขอนี้เองได้:

```
PATCH /rest/v1/profiles?id=eq.<uuid ของตัวเอง>
Body: { "role": "admin" }
```

ไล่ migration ทั้ง 18 ไฟล์แล้ว **ไม่มีอะไรกันไว้เลย** — ไม่มี trigger ตรวจการเปลี่ยน role
ไม่มีการจำกัดสิทธิ์ระดับคอลัมน์บน `profiles` และ Supabase ให้สิทธิ์ระดับตารางแก่
`authenticated` มาตั้งแต่ต้น (หลักฐาน: migration 016 ต้องเขียน
`revoke select on public.candidates from anon, authenticated` อย่างชัดเจน
แปลว่ามีการ grant ทั่วทั้งสคีมาอยู่จริง)

**ยืนยันกับฐานข้อมูลจริงแล้วเมื่อ 2026-09-08** — `information_schema.role_table_grants`
คืนสิทธิ์ครบทุกชนิดให้ทั้ง `anon` และ `authenticated` บน `public.profiles`:
INSERT / SELECT / UPDATE / DELETE / TRUNCATE / REFERENCES / TRIGGER
**ช่องโหว่มีจริง ไม่ใช่ข้อสงสัย**

**สถานะ: ✅ ปิดแล้ว ยืนยันด้วย break check เมื่อ 2026-09-08**
รัน migration แล้วเทสต์เขียว 2/2 · เปิดช่องกลับด้วย
`grant update on public.profiles to authenticated` แล้วเทสต์**แดง 1 ตัวที่บรรทัด 50**
ตามที่คาดไว้ · รันไฟล์ 019 ซ้ำแล้วกลับมาเขียว 2/2

| ไฟล์ | คืออะไร |
|---|---|
| `supabase/migrations/019_lock_profile_columns.sql` | ถอน UPDATE ระดับตาราง แล้วคืนเฉพาะ `display_name` กับ `settings` · ถอน INSERT/DELETE/TRUNCATE ที่ไม่มีใครใช้ด้วย |
| `supabase/migrations/019_lock_profile_columns.int.test.ts` | เทสต์ 2 ตัวที่เดินเส้นทางเดียวกับผู้โจมตีจริง |

หลักการเดียวกับ migration 016 — **RLS กรอง "แถว" ส่วน column grant กรอง "คอลัมน์"
ต้องมีทั้งคู่** การเปลี่ยน role ของแอดมินยังทำได้ เพราะไปผ่าน `POST /api/admin/users`
ซึ่งใช้ service-role client ที่ bypass ทั้ง RLS และ grant

**เทสต์จงใจไม่ตรวจแค่หน้าจอ** — เทสต์ที่ยืนยันว่า "หน้า /settings ไม่มีช่องแก้ role"
จะเขียวได้ทั้งที่ช่องโหว่ยังเปิดอยู่ เพราะช่องโหว่ไม่ได้อยู่ที่หน้าจอ เทสต์นี้จึงสร้าง
บัญชีจริง ล็อกอินด้วย anon key แล้วยิง PATCH ตรงไปที่ PostgREST และ**ตรวจค่าใน
ฐานข้อมูลซ้ำ** ไม่ได้เชื่อค่า `error` อย่างเดียว

#### ลำดับการรัน

1. รัน `019_lock_profile_columns.sql` ใน Supabase SQL editor
2. `npx vitest run supabase/migrations/019_lock_profile_columns.int.test.ts` → ต้องเขียว
3. **break check** — รันคำสั่งนี้เพื่อเปิดช่องโหว่กลับชั่วคราว แล้วรันเทสต์ซ้ำ
   **ต้องแดง 1 ตัว** (ถ้ายังเขียวแปลว่าเทสต์ไม่ได้ตรวจอะไรเลย)
   ```sql
   grant update on public.profiles to authenticated;
   ```
4. ปิดกลับด้วยการรัน `019_lock_profile_columns.sql` ซ้ำ (คำสั่งทั้งไฟล์รันซ้ำได้)

### B1 — กราฟบน Dashboard

**ที่ตัดสินไว้** ทำกราฟเพิ่ม ตัด Trend Analysis ออก
**ทำอะไร** เพิ่มสองกราฟใต้การ์ดตัวเลขสามใบที่มีอยู่

1. **ทักษะที่พบบ่อย** — แท่งแนวนอน 10 อันดับแรก (ตรงกับ 1.3.1.3 ข้อ 2 ในเล่ม)
2. **จำนวนผู้สมัครตามแหล่งที่มา** — แท่งแนวนอน 4 แท่ง (`synthetic`/`csv`/`upload`/`scraper`)

**ทำไมเลือกสองตัวนี้** ทั้งคู่ตอบได้จากข้อมูลที่มีอยู่แล้วโดยไม่ต้องตีความ
กราฟแหล่งที่มายังเป็นหลักฐาน PDPA ที่ใช้งานได้จริงด้วย — เห็นทันทีว่าข้อมูล
กี่เปอร์เซ็นต์มาจากการดึงอัตโนมัติ

#### ตัดสินใจเชิงเทคนิค 3 ข้อ

**1. นับใน SQL ไม่ใช่ใน JavaScript**

ตาราง `candidate_skills` มีได้หลายหมื่นแถว การดึงมานับใน server component
คือการโหลดทั้งตารางทุกครั้งที่เปิดหน้า Dashboard จึงทำเป็น SQL function สองตัว
ใน migration ใหม่ (**020** — 019 ถูกใช้กับ B0 ไปแล้ว)

```sql
-- 10 อันดับทักษะที่พบบ่อยที่สุด
create or replace function top_skills(p_limit int default 10)
returns table (name text, cnt bigint) ...

-- จำนวนผู้สมัครแยกตามแหล่งที่มา
create or replace function candidate_source_counts()
returns table (source text, cnt bigint) ...
```

**ข้อควรระวังที่ต้องทำตาม** (จากบทเรียนของ migration 017)
- `search_path` ต้องมี `extensions` ด้วยเสมอ
- ถอน EXECUTE จาก **PUBLIC** ด้วย ไม่ใช่แค่ `anon` กับ `authenticated`
  แล้ว grant ให้ `service_role` — สองฟังก์ชันนี้เปิดเผยภาพรวมของฐานข้อมูลทั้งก้อน
  จึงไม่ควรเรียกได้จากเบราว์เซอร์ด้วยคีย์สาธารณะ

**2. วาดกราฟด้วย SVG เอง ไม่เพิ่มไลบรารี**

ทั้งสองกราฟเป็นแท่งแนวนอน ซึ่งคือ `<div>` ที่กำหนดความกว้างเป็นเปอร์เซ็นต์
การเพิ่ม Chart.js หรือ Recharts เข้ามาเพื่อสิ่งนี้จะเพิ่มขนาด bundle
ให้ทุกหน้าโดยได้ประโยชน์เท่าเดิม และทำให้ Dashboard ต้องกลายเป็น client component
ซึ่งตอนนี้เป็น server component ที่อ่านข้อมูลตรงจากฐานได้เลย

สร้าง `components/dashboard/BarList.tsx` เป็นคอมโพเนนต์เดียวใช้ทั้งสองกราฟ
รับ `{ label, value }[]` แล้ววาดแท่งเทียบกับค่าสูงสุด ใช้ตัวแปรสีจาก `globals.css`
ที่มีอยู่แล้ว

**3. ต้องแยก "ไม่มีข้อมูล" ออกจาก "อ่านข้อมูลไม่ได้"**

กฎเดิมของโปรเจกต์ — `.rpc()` ต้องเช็ค `error` เสมอ ถ้า RPC พังแล้วเราวาดกราฟเปล่า
ผู้ใช้จะเห็น "ยังไม่มีทักษะในระบบ" ทั้งที่มีข้อมูลอยู่เต็มฐาน ซึ่งเป็นบั๊กแบบเดียวกับ
ที่เคยทำให้หน้าค้นหาขึ้น "ไม่พบผลลัพธ์" ตอนที่ระบบค้นหาพังสนิท

#### ลำดับงาน (TDD)

| ขั้น | ทำอะไร | เทสต์ |
|---|---|---|
| 1 | `components/dashboard/BarList.tsx` | unit: ค่าสูงสุดได้ 100% · ค่า 0 ไม่ทำให้หารด้วยศูนย์ · รายการว่างแสดงข้อความแทนกราฟ |
| 2 | migration 020 + สิทธิ์ | integration: เรียก RPC ทั้งสองแล้วได้รูปทรงถูก |
| 3 | ต่อเข้าหน้า Dashboard + เช็ค `error` | break check: ทำให้ RPC พัง แล้วต้องเห็นข้อความผิดพลาด ไม่ใช่กราฟเปล่า |

### B2 — เปลี่ยนชื่อผู้ใช้ในหน้าตั้งค่า

**ที่ตัดสินไว้** เพิ่มให้เปลี่ยนชื่อได้ (Use case 6 ในเล่มบอกว่าเปลี่ยนได้ทั้งชื่อและรหัสผ่าน
แต่ระบบจริงเปลี่ยนได้แค่รหัสผ่าน)

> **ข้อนี้ไม่ใช่งานเล็กอย่างที่ประเมินไว้ตอนถาม** — ตรวจโค้ดแล้วพบเรื่องที่ต้องแก้ก่อน

#### ปัญหาที่เจอ

คอลัมน์ `profiles.display_name` **มีอยู่แล้ว** และ migration 003 ก็อนุญาตให้ผู้ใช้
แก้แถวของตัวเองได้แล้ว ดูเผินๆ เหมือนเหลือแค่เพิ่มช่องกรอก แต่:

**ตอนนี้ `display_name` ถูกใช้เป็น "อีเมล" ไม่ใช่ "ชื่อเล่น"**

trigger ใน migration 002 ใส่ค่าตอนสมัครว่า `values (new.id, new.email, 'member')`
คือ**เอาอีเมลมาใส่ในช่องชื่อ** และตาราง `profiles` ไม่มีคอลัมน์อีเมลแยกเลย
ผลคือ `display_name` เป็นที่เดียวในแอปที่มองเห็นอีเมลของผู้ใช้ได้

ถ้าเปิดให้แก้ได้เลยจะพังสามที่พร้อมกัน

| ที่ | อาการ |
|---|---|
| หน้า `/admin/users` | แสดง `display_name ?? id` เท่านั้น — ผู้ใช้เปลี่ยนชื่อเป็น "ตั้ม" แล้วแอดมินจะแยกไม่ออกว่าใครเป็นใคร เหลือแต่ uuid ให้เดา |
| `README.md` | บอกวิธีตั้งแอดมินว่า `update profiles set role='admin' where display_name='<your-email>'` — คำสั่งนี้จะหาไม่เจอเงียบๆ (UPDATE 0 rows ไม่ใช่ error) |
| `activity_log` | หน้ากิจกรรมย้อนชื่อผู้ทำจาก `display_name` — ผู้ใช้ตั้งชื่อตัวเองเป็นอีเมลของคนอื่นได้ ทำให้บันทึกกิจกรรมชี้ไปผิดคน ซึ่งเป็นปัญหาหนักกว่าสองข้อบน เพราะ `activity_log` มีไว้เพื่อตอบว่า "ใครทำ" |

#### ทางแก้ที่เสนอ

**เพิ่มคอลัมน์ `profiles.email` (migration 021) ที่ผู้ใช้แก้ไม่ได้**

1. เพิ่มคอลัมน์ `email text` แล้ว backfill จาก `auth.users` ครั้งเดียว
2. แก้ trigger `handle_new_user()` ให้เขียนทั้ง `email` และ `display_name` ตอนสมัคร
3. **`email` แก้ไม่ได้อยู่แล้วหลัง migration 019** เพราะ 019 คืนสิทธิ์ UPDATE ให้เฉพาะ
   `display_name` กับ `settings` คอลัมน์ใหม่ที่เพิ่มทีหลังจะไม่ได้สิทธิ์โดยอัตโนมัติ —
   **นี่คือพฤติกรรมที่ต้องการ และเป็นเหตุผลที่ต้องทำ 019 ก่อน**
4. `/admin/users` แสดงอีเมลเป็นบรรทัดหลัก และชื่อที่ตั้งเองเป็นบรรทัดรอง
5. `activity_log` แสดงชื่อที่ตั้งเอง **พร้อมอีเมลกำกับ** เพื่อไม่ให้ปลอมตัวได้
6. แก้ `README.md` ให้ใช้ `where email = '<your-email>'`
7. เพิ่มการ์ด "ชื่อที่แสดง" ใน `/settings` — งานที่ผู้ใช้ขอ อยู่ท้ายสุด

#### ลำดับงาน (TDD)

| ขั้น | ทำอะไร | เทสต์ |
|---|---|---|
| 1 | migration 021: คอลัมน์ `email` + backfill + trigger | integration: สมัครใหม่แล้วได้ `email` ครบ · ผู้ใช้แก้ `email` ไม่ได้ |
| 2 | `/admin/users` + `activity_log` อ่านอีเมล | unit: แถวที่ `display_name` ว่างต้องแสดงอีเมล ไม่ใช่ uuid |
| 3 | การ์ดเปลี่ยนชื่อใน `/settings` | unit: ชื่อว่างล้วนต้องบันทึกไม่ได้ · ตัดช่องว่างหัวท้าย · จำกัดความยาว |
| 4 | break check ขั้น 1 | เพิ่ม `grant update (email)` ชั่วคราวแล้วเทสต์ "แก้ email ไม่ได้" ต้องแดง |

**ขั้น 1 ต้องเสร็จก่อนขั้น 3 เสมอ** ถ้าปล่อยให้แก้ชื่อได้ก่อนที่จะมีคอลัมน์อีเมล
จะมีช่วงที่แอดมินระบุตัวผู้ใช้ไม่ได้
