## หมายเหตุร่วมทุกตาราง

- **Primary Key ทุกตารางเป็น `uuid`** ไม่ใช่ `Integer` แบบ auto-increment
  เหตุผล: รหัสแบบเรียงลำดับทำให้เดาได้ว่าในระบบมีข้อมูลกี่แถวและอ้างถึงแถวอื่นได้
  ด้วยการเดาเลข ซึ่งเป็นความเสี่ยงเมื่อข้อมูลเป็นข้อมูลบุคคล
- **`timestamptz`** = timestamp พร้อม time zone (PostgreSQL) เก็บเป็น UTC
- **`vector(768)`** = ชนิดข้อมูลจาก extension pgvector เก็บเวกเตอร์ 768 มิติ
- **`jsonb`** = JSON แบบ binary ค้นหาและทำดัชนีได้

> `.tsx` หรือ `.sql` ไฟล์ใดอ้างถึงเลย — ไม่ถูกเขียน ไม่ถูกอ่าน ไม่แสดงผลที่ไหน
> **ยังไม่ลบทิ้งเพราะกติกาของโปรเจกต์ห้ามแก้โครงสร้างตาราง `jobs`** เดิมน่าจะเก็บ
> ลิงก์ไปยังประกาศงานต้นทางตอนที่ข้อมูลถูกดึงมาจากภายนอก

> Dictionary เทียบกับฐานจริงแล้วเจอคอลัมน์ที่เอกสารไม่พูดถึง
>
> **`created_at` เป็น `timestamp` ไม่มี time zone ต่างจากทุกตารางที่โปรเจกต์นี้สร้างเอง**
> (ที่เหลือใช้ `timestamptz`) เพราะมาจากสคริปต์คนละยุค **วันนี้ยังไม่เป็นปัญหา**
> เพราะค่านี้ถูกใช้เพื่อ**เรียงลำดับอย่างเดียว** (`app/(app)/jobs/page.tsx`)
> ไม่เคยถูกแสดงให้ผู้ใช้เห็น และทุกค่ามาจาก `now()` บนเซิร์ฟเวอร์เดียวกันจึงเทียบกันได้
> **แต่ถ้าวันไหนเอาไปแสดงเป็นวันที่ ต้องระวัง** — Supabase เก็บเป็น UTC โดยไม่มี
> offset ติดมาด้วย ถ้าฝั่งแอปตีความว่าเป็นเวลาท้องถิ่นจะเพี้ยนไป 7 ชั่วโมง

> **เวกเตอร์ของตำแหน่งงานและของผู้สมัครใช้โมเดลและจำนวนมิติเดียวกัน** จึงอยู่ใน
> ปริภูมิเดียวกันและเปรียบเทียบข้ามกันได้โดยตรง นี่คือเงื่อนไขทางเทคนิคข้อเดียว
> ที่ทำให้การจับคู่สองทิศ (หางานให้คน / หาคนให้งาน) ใช้กลไกเดียวกันได้

## ฟังก์ชันในฐานข้อมูล (เพิ่มเป็นหัวข้อ 3.6.1)

เล่มเดิมไม่มีหัวข้อนี้ แต่ตรรกะการค้นหาหลักของระบบอยู่ในฐานข้อมูล ไม่ใช่ในโค้ด
จึงควรบันทึกไว้

| ฟังก์ชัน | หน้าที่ |
|---|---|
| `match_candidates(query_embedding, match_count)` | จัดอันดับผู้สมัครตามความใกล้เคียงเชิงโคไซน์กับเวกเตอร์คำค้นหา |
| `match_candidates_filtered(...)` | เหมือนข้างบน แต่**กรองเงื่อนไขเข้ม (ประสบการณ์/สาขา/ทักษะ) ใน SQL ก่อนจัดอันดับ** |
| `match_jobs(query_embedding, match_count)` | ภาพสะท้อนของตัวแรก ใช้หาตำแหน่งงานที่เหมาะกับโปรไฟล์ |
| `duplicate_candidate_names()` | คืนชื่อที่ปรากฏมากกว่าหนึ่งครั้ง ใช้ติดป้ายเตือนข้อมูลซ้ำ |

> **ทั้งสี่ฟังก์ชันเรียกได้เฉพาะจากฝั่งเซิร์ฟเวอร์** สิทธิ์ EXECUTE ถูกถอนจากผู้ใช้
> ทุกระดับที่เข้าถึงผ่านเบราว์เซอร์ เพื่อไม่ให้ผู้ที่ล็อกอินแล้วเรียกฟังก์ชันเหล่านี้
> ตรงๆ ด้วยคีย์สาธารณะเพื่อดึงข้อมูลออกไปทั้งหมด
>
> **เหตุผลที่กรองก่อนจัดอันดับ ไม่ใช่จัดอันดับแล้วค่อยกรอง** ถ้าดึง 50 อันดับแรกมา
> แล้วค่อยกรองในโค้ด ผู้สมัครที่ตรงเงื่อนไขแต่คะแนนความใกล้เคียงอยู่อันดับ 51
> จะหายไปโดยไม่มีใครรู้ การกรองใน SQL ก่อนทำให้การจัดอันดับเกิดขึ้นบนกลุ่ม
> ที่ผ่านเงื่อนไขแล้วเสมอ
