## 3. กรณีที่ไม่ผ่าน

### 3.1 SR-04 — ระบบคืนผู้สมัครแม้ไม่มีผู้ใดเกี่ยวข้องกับคำค้น

**สิ่งที่คาดหวัง** ค้นด้วยคำที่ไม่มีผู้สมัครคนใดตรงเลย ระบบควรแจ้งว่าไม่พบผลลัพธ์

**สิ่งที่เกิดขึ้น** ระบบคืนผู้สมัคร 20 คนพร้อมคะแนนความใกล้เคียง

**สาเหตุ** การค้นหาของระบบใช้การเปรียบเทียบเวกเตอร์ (cosine similarity) ซึ่ง
**คืนเพื่อนบ้านที่ใกล้ที่สุดเสมอ** โดยไม่มีแนวคิดเรื่อง "ใกล้ไม่พอ" ต่างจากการ
ค้นหาด้วยคำสำคัญที่ไม่เจอคำก็คือไม่เจอ

**การตัดสินใจ: ไม่แก้ พร้อมเหตุผลที่วัดได้** ได้ทดลองหาเกณฑ์คะแนนขั้นต่ำเพื่อ
แจ้งเตือนผู้ใช้ โดยวัดคะแนนสูงสุดของคำค้นสองกลุ่ม

| คำค้น | ควรพบผู้สมัครหรือไม่ | คะแนนสูงสุด |
|---|---|---:|
| Supply Chain Manager | ควรพบ | 67 |
| Finance Analyst ประสบการณ์ 3 ปี | ควรพบ | 66 |
| พระสงฆ์ (Monk) | ไม่ควรพบ | 64 |
| นักบินอวกาศ (Astronaut) | ไม่ควรพบ | 59 |
| กรรมการมวย (Boxing Referee) | ไม่ควรพบ | 56 |

คะแนนต่ำสุดของกลุ่มที่ควรพบคือ 66 ส่วนคะแนนสูงสุดของกลุ่มที่ไม่ควรพบคือ 64
**ห่างกันเพียง 2 คะแนน และช่วงคะแนนของสองกลุ่มทับซ้อนกัน** จึงไม่มีค่าใดที่แยก
สองกลุ่มออกจากกันได้ การกำหนดเกณฑ์โดยไม่มีข้อมูลรองรับจะทำให้เกิดความผิดพลาด
ทั้งสองทาง คือซ่อนผู้สมัครที่ควรพบ และยังคงแสดงผู้สมัครที่ไม่เกี่ยวข้องอยู่ดี

**ข้อจำกัดของการวัด** ใช้ฐานข้อมูลผู้สมัคร 164 ราย ซึ่งส่วนใหญ่เป็นข้อมูลสังเคราะห์
ที่กระจุกอยู่ในไม่กี่สายอาชีพ ค่าคะแนนจึงมีแนวโน้มอัดตัวอยู่ในช่วงแคบ
หากมีข้อมูลจริงหลากหลายกว่านี้ ผลอาจเปลี่ยนไป ควรวัดซ้ำก่อนสรุปเป็นข้อยุติ

**ผลต่อการใช้งาน** ผู้ใช้ต้องอ่านคะแนนประกอบเสมอ ไม่ใช่ถือว่าทุกคนในผลลัพธ์คือ
ผู้ที่ตรงเงื่อนไข ซึ่งสอดคล้องกับข้อกำหนดการใช้งานข้อ 4 ที่ห้ามใช้คะแนนจาก
ปัญญาประดิษฐ์ตัดสินบุคคลโดยลำพัง

### 3.2 ST-13 — ไม่มีการตรวจความยาวชื่อที่แสดงฝั่งเซิร์ฟเวอร์

**สิ่งที่คาดหวัง** ควรมีการตรวจความยาวอย่างน้อยหนึ่งชั้นนอกเหนือจากหน้าจอ

**สิ่งที่เกิดขึ้น** ไม่มีเลยสักชั้น ตรวจแล้วสามจุด

| ชั้น | ผลการตรวจ |
|---|---|
| เส้นทางของแอปพลิเคชัน | ไม่มี API route ใดเขียนคอลัมน์นี้ — หน้าจอเขียนลงฐานข้อมูลผ่าน PostgREST โดยตรง |
| โครงสร้างตาราง | คอลัมน์เป็นชนิด `text` ไม่กำหนดความยาวสูงสุด และไม่มี CHECK constraint |
| สิทธิ์การเขียน | migration 019 ให้สิทธิ์ `UPDATE` คอลัมน์นี้แก่ผู้ใช้ที่เข้าสู่ระบบโดยตรง |

ด่านเดียวที่มีคือแอตทริบิวต์ `maxLength` ในช่องกรอก ซึ่งกันได้เฉพาะการพิมพ์และ
การวางข้อความในหน้าจอเท่านั้น

**เปรียบเทียบกับกรณีที่ผ่าน (JB-11)** การสร้างตำแหน่งงานผ่าน API route ที่มี
ตัวตรวจสอบ (`lib/jobs/validate.ts`) เมื่อยิงคำขอที่ความยาวเกินเพดาน ระบบตอบ
สถานะ 400 พร้อมข้อความ "ตำแหน่งงานยาวเกินไป (256 ตัวอักษร สูงสุด 255)"
ซึ่งระบุทั้งค่าที่ส่งมาและเพดานที่รับได้

**สองกรณีนี้มีลักษณะเหมือนกันบนหน้าจอ แต่มีด่านตรวจจริงไม่เท่ากัน** และความต่าง
นี้มองไม่เห็นจากการทดสอบผ่านหน้าจอเพียงอย่างเดียว

**ขอบเขตความเสี่ยง** จำกัดอยู่ที่ข้อมูลของผู้ใช้เอง เนื่องจากนโยบาย RLS และ
migration 019 อนุญาตให้แก้ได้เฉพาะแถวของตนเอง จึงไม่ใช่ช่องโหว่ด้านสิทธิ์
แต่เป็นปัญหาความทนทานของหน้าจอที่แสดงชื่อนั้น ได้แก่ หน้าจัดการผู้ใช้และ
บันทึกกิจกรรม

**การตัดสินใจ: บันทึกไว้เป็นข้อจำกัดที่ทราบ ไม่แก้ก่อนส่ง** เนื่องจากต้องเพิ่ม
API route ใหม่พร้อมชุดทดสอบ ซึ่งเป็นการเปลี่ยนโครงสร้างที่ไม่ควรทำในช่วงท้าย
และความเสี่ยงจำกัดอยู่ในวงแคบ

## 4. ข้อจำกัดของระบบที่พบระหว่างการทดสอบ

ข้อต่อไปนี้ไม่ได้ทำให้กรณีทดสอบใดไม่ผ่าน แต่เป็นข้อเท็จจริงเกี่ยวกับระบบที่
ควรบันทึกไว้

### 4.1 ผลลัพธ์จากปัญญาประดิษฐ์ไม่คงที่ถึงขั้นเปลี่ยนโครงสร้างเงื่อนไข

ระหว่างทดสอบพบว่าการค้นด้วยข้อความเดียวกันในเวลาต่างกัน ระบบแยกเงื่อนไขออกมา
ไม่เหมือนกัน

| ครั้งที่ | ข้อความค้นหา | เงื่อนไขทักษะที่ระบบแยกได้ |
|---|---|---|
| 1 | Data Scientist | `Data Science` |
| 2 | Data Scientist | ไม่มีเลย |
| 3 | UX Designer | `UX` |
| 4 | UX Designer | `UX Design` |

เอกสารประกอบระบบเคยบันทึกไว้แล้วว่าคะแนนความเหมาะสมที่ได้จากแบบจำลองแกว่งได้
ประมาณ 10 คะแนนจากข้อมูลนำเข้าชุดเดียวกัน **สิ่งที่พบครั้งนี้รุนแรงกว่า
เพราะไม่ใช่ค่าตัวเลขที่ต่างกัน แต่เป็นการมีหรือไม่มีเงื่อนไขคัดกรอง**

รูปแบบความคลาดเคลื่อนที่สังเกตได้คือ แบบจำลองนำ**ชื่อตำแหน่งงานมาแปลงเป็นทักษะ**
("Data Scientist" → "Data Science") ซึ่งไม่ใช่ทักษะ และเป็นข้อความที่อยู่ในส่วน
คำค้นเชิงความหมายอยู่แล้ว จึงเท่ากับนับซ้ำสองครั้ง

แนวทางแก้คือปรับคำสั่งที่ส่งให้แบบจำลอง แต่**ผลของการปรับคำสั่งพิสูจน์ด้วยชุดทดสอบ
อัตโนมัติไม่ได้** ต้องวัดซ้ำหลายรอบด้วยวิธีเดียวกับที่ใช้เปรียบเทียบรุ่นของแบบจำลอง
จึงไม่ดำเนินการในรอบนี้ และบันทึกเป็นงานต่อยอด

### 4.2 คิวรอตรวจสอบยังไม่มีเส้นทางเข้าถึงในเวอร์ชันนี้

ระบบมีกลไกคัดกรองผู้สมัครที่ข้อมูลไม่ครบเข้าคิวรอการตรวจสอบ พร้อมชุดทดสอบ
อัตโนมัติครอบคลุมแล้ว แต่**ฟังก์ชันคัดกรองถูกเรียกจากสคริปต์ดึงข้อมูลอัตโนมัติ
เพียงที่เดียว** ส่วนการนำเข้าไฟล์ด้วยมือผ่านหน้าเว็บไม่ผ่านตัวคัดกรอง ข้อมูลจึง
เข้าตารางผู้สมัครโดยตรงทุกแถวไม่ว่าจะครบหรือไม่

สคริปต์ดึงข้อมูลอัตโนมัติยังปิดการทำงานอยู่เนื่องจากยังไม่มีบัญชีบริการภายนอก
**คิวรอตรวจสอบจึงเป็นฟังก์ชันที่มีอยู่จริงในรหัสต้นฉบับแต่ยังเปิดใช้งานไม่ได้**
กรณีทดสอบ DM-10 และ DM-11 ถูกปรับให้ระบุข้อเท็จจริงนี้แทนการรายงานว่าไม่ผ่าน

### 4.3 ผู้ดูแลระบบยังเปลี่ยนสิทธิ์ผู้ดูแลระบบคนอื่นได้

ระบบป้องกันการลดสิทธิ์ของตนเองแล้ว (กรณี AD-02 ผ่าน) แต่ยังไม่ได้ป้องกันการลด
สิทธิ์ของผู้ดูแลระบบรายอื่น และไม่รับประกันว่าระบบจะเหลือผู้ดูแลระบบอย่างน้อย
หนึ่งรายเสมอ เนื่องจากผู้ดูแลระบบสองรายที่ลดสิทธิ์ของอีกฝ่ายพร้อมกันจะผ่าน
การตรวจสอบทั้งคู่ ข้อจำกัดนี้ถูกบันทึกไว้ในรหัสต้นฉบับตั้งแต่ตอนพัฒนา

### 4.4 อีเมลของระบบส่งจากโดเมนของผู้ให้บริการ

อีเมลยืนยันการสมัครและอีเมลตั้งรหัสผ่านใหม่ส่งจาก `mail.app.supabase.io`
ซึ่งเป็นค่าตั้งต้นของผู้ให้บริการ ใช้งานได้ปกติในการทดสอบ แต่หากนำไปใช้จริง
ในองค์กรควรตั้งค่าเซิร์ฟเวอร์ส่งอีเมลของตนเอง เพื่อให้ผู้รับตรวจสอบแหล่งที่มาได้

นอกจากนี้โควตาการส่งอีเมลของบริการระดับฟรีมีจำกัดมาก ระหว่างการทดสอบพบว่าเมื่อ
ส่งถี่เกินไป ระบบตอบข้อความผิดพลาดที่ทำให้เข้าใจผิดว่าอีเมลนั้นใช้สมัครไม่ได้
ทั้งที่เป็นเพียงข้อจำกัดชั่วคราว — ได้แก้ข้อความให้ตรงกับสาเหตุจริงแล้ว

### 4.5 การถอดชื่อเฉพาะจากเอกสารยังไม่แม่นยำ

การอ่านเรซูเม่ด้วยแบบจำลองภาษายังถอดชื่อบุคคลและชื่อเฉพาะได้ไม่แม่นยำเท่าที่ควร
ระบบจึงออกแบบให้ผู้ใช้**ตรวจและยืนยันข้อมูลที่ถอดได้ก่อนบันทึกเสมอ** ซึ่งเป็น
การออกแบบที่รองรับข้อจำกัดนี้อยู่แล้ว ไม่ใช่การแก้ปัญหาภายหลัง

---

## 5. งานต่อยอด

1. ปรับคำสั่งที่ส่งให้แบบจำลองไม่ให้แปลงชื่อตำแหน่งงานเป็นทักษะ พร้อมวัดผลซ้ำ
   อย่างน้อยสามรอบก่อนสรุป (จากข้อ 4.1)
2. เพิ่มการตรวจความยาวชื่อที่แสดงฝั่งเซิร์ฟเวอร์ (จากข้อ 3.2)
3. เชื่อมต่อบัญชีบริการดึงข้อมูลเพื่อเปิดใช้คิวรอตรวจสอบ (จากข้อ 4.2)
4. ป้องกันไม่ให้ระบบเหลือผู้ดูแลระบบน้อยกว่าหนึ่งราย (จากข้อ 4.3)
5. วัดเกณฑ์คะแนนขั้นต่ำซ้ำเมื่อมีข้อมูลผู้สมัครจริงที่หลากหลายขึ้น (จากข้อ 3.1)
