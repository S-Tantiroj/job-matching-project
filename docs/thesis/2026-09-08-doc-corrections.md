## หมวด ก. แก้ให้ตรงของจริง

### 1. ตัด Express.js ออก (หัวข้อ 2.3.2)

**เล่มเขียนว่า** "2.3.2) Node.js และ Express.js ... Express.js เป็น Framework ที่ทำงานบน
Node.js ใช้สำหรับสร้าง RESTful API"

**ของจริง** ไม่มี Express ใน `package.json` เลย dependencies ทั้งหมดมี 8 ตัว:
`next`, `react`, `react-dom`, `@supabase/ssr`, `@supabase/supabase-js`, `@google/genai`,
`lucide-react`, `papaparse` — API ทั้งหมดเป็น **Route Handler ของ Next.js App Router**
(ไฟล์ `app/api/**/route.ts`) ซึ่งรันบน Node runtime ของ Next.js เอง

**แก้เป็น** เปลี่ยนหัวข้อเป็น "2.3.2) Node.js และ Next.js Route Handler" แล้วเขียนย่อหน้าที่สองใหม่:

> โครงงานนี้ไม่ได้แยก Backend Framework ออกมาต่างหาก แต่ใช้ความสามารถ Route Handler
> ของ Next.js App Router สร้าง REST API ภายในโปรเจกต์เดียวกับ Frontend (ไฟล์
> `app/api/<ชื่อ>/route.ts` แต่ละไฟล์คือหนึ่ง endpoint) วิธีนี้ทำให้ Frontend และ Backend
> ใช้ TypeScript ชุดเดียวกัน แชร์ type ของข้อมูลได้โดยตรง และ deploy เป็นแอปเดียว

**เพราะอะไร** เขียนว่าใช้ Express ทั้งที่ไม่มีอยู่ในระบบ = กรรมการเปิด `package.json`
แล้วเจอทันทีว่าไม่ตรง

### 2. ตัดหัวข้อ Docker ออกทั้งหัวข้อ (หัวข้อ 2.3.4)

**เล่มเขียนว่า** "2.3.4) Docker ... แพ็กแอปพลิเคชันและสิ่งแวดล้อมทั้งหมดไว้ใน Container เดียว"

**ของจริง** ไม่มี `Dockerfile`, ไม่มี `docker-compose.yml`, ไม่มีอะไรเกี่ยวกับ container
ในรีโปเลย ระบบ deploy บน **Vercel** ซึ่งเป็น serverless platform ที่ build จาก git โดยตรง
ส่วนฐานข้อมูลเป็น **Supabase cloud** ไม่ได้รันเอง

**แก้เป็น** ลบ 2.3.4 ทิ้ง แล้วเลื่อนเลข RAG จาก 2.3.5 → 2.3.4 **หรือ** ถ้าอยากคงจำนวนหัวข้อไว้
ให้เปลี่ยนเป็น "2.3.4) Vercel และการ Deploy":

> Vercel เป็นแพลตฟอร์มสำหรับ deploy เว็บแอปพลิเคชันแบบ Serverless พัฒนาโดยผู้สร้าง
> Next.js เอง เมื่อ push โค้ดขึ้น Git ระบบจะ build และ deploy ให้อัตโนมัติ โดยแต่ละ
> API Route ถูกแปลงเป็น Serverless Function ที่ขยายตัวตามปริมาณการใช้งาน
> โครงงานนี้จึงไม่ต้องจัดการ Container หรือเซิร์ฟเวอร์เอง

**เพราะอะไร** Docker แก้ปัญหา "สิ่งแวดล้อมแต่ละเครื่องไม่เหมือนกัน" ซึ่งเป็นปัญหาที่
สถาปัตยกรรมนี้ไม่มีตั้งแต่แรก การเขียนถึงมันจึงไม่ใช่แค่ผิด แต่ทำให้เหตุผลการเลือก
เทคโนโลยีทั้งหมวดฟังดูไม่เชื่อมกัน

### 3. เขียนหัวข้อฐานข้อมูลใหม่เป็น Supabase + pgvector (หัวข้อ 2.3.3 และ 1.3.3.1)

**เล่มเขียนว่า** "2.3.3) PostgreSQL เป็นระบบฐานข้อมูลเชิงสัมพันธ์ ที่มีความเสถียร..."
(สามบรรทัด ไม่พูดถึง Supabase หรือ vector เลย) และ 1.3.3.1 ข้อ 1) "ใช้ PostgreSQL ในการจัดเก็บข้อมูล"

**ของจริง** ใช้ **Supabase** ซึ่งเป็น Postgres + Auth + Storage + REST API ในตัว และ
**ติดตั้ง extension `pgvector`** เก็บ embedding เป็นชนิด `vector(768)` ในคอลัมน์
`candidates.embedding`, `jobs.embedding`, `self_profiles.embedding` การค้นหาเชิงความหมาย
ทำด้วยตัวดำเนินการ `<=>` (cosine distance) ผ่าน SQL function สี่ตัว
(`match_candidates`, `match_candidates_filtered`, `match_jobs`, `duplicate_candidate_names`)

**แก้เป็น** แทนที่ 2.3.3 ทั้งหัวข้อด้วย:

> **2.3.3) Supabase และ PostgreSQL (pgvector)**
>
> Supabase เป็นแพลตฟอร์มฐานข้อมูลที่สร้างบน PostgreSQL โดยเพิ่มระบบยืนยันตัวตน
> (Authentication), การจัดเก็บไฟล์ (Storage), REST API อัตโนมัติ และระบบควบคุมสิทธิ์
> ระดับแถว (Row Level Security) มาให้ในตัว โครงงานนี้ใช้ Supabase เป็นทั้งฐานข้อมูล
> และระบบจัดการผู้ใช้ จึงไม่ต้องเก็บรหัสผ่านเอง
>
> ส่วนสำคัญที่สุดต่อโครงงานนี้คือ extension **pgvector** ซึ่งเพิ่มชนิดข้อมูล `vector`
> ให้ PostgreSQL ทำให้เก็บเวกเตอร์ความหมาย (Embedding) ขนาด 768 มิติไว้ใน
> ตารางเดียวกับข้อมูลปกติได้ และค้นหาด้วยความใกล้เคียงเชิงโคไซน์ผ่านตัวดำเนินการ `<=>`
> ได้ในคำสั่ง SQL เดียว จุดนี้คือสิ่งที่ทำให้สถาปัตยกรรม RAG ในหัวข้อ 2.3.5 ทำงานได้จริง
> โดยไม่ต้องติดตั้งฐานข้อมูลเวกเตอร์แยกอีกตัว
>
> ข้อมูลผู้สมัครและข้อมูลตำแหน่งงานถูก Embedding ด้วยโมเดลเดียวกันและจำนวนมิติเดียวกัน
> จึงอยู่ใน "ปริภูมิเวกเตอร์" เดียวกัน ทำให้เปรียบเทียบข้ามกันได้โดยตรง — เป็นเงื่อนไข
> ที่ทำให้การจับคู่ผู้สมัครกับตำแหน่งงานเกิดขึ้นได้

และแก้ 1.3.3.1 ข้อ 1) เป็น "ใช้ Supabase (PostgreSQL + pgvector) ในการจัดเก็บข้อมูล
และค้นหาเชิงความหมาย"

**เพราะอะไร** เล่มประกาศว่าใช้สถาปัตยกรรม RAG (2.3.5) และอธิบายว่าต้อง "จัดเก็บใน
ฐานข้อมูลเวกเตอร์" แต่หัวข้อฐานข้อมูลกลับไม่บอกว่าฐานข้อมูลเวกเตอร์คืออะไร
ตอนนี้สองหัวข้อขัดกันเอง

### 4. ตาราง Users ไม่มีคอลัมน์ password (ตารางที่ 3-6)

**เล่มเขียนว่า**

| Field | Type | Description |
|---|---|---|
| user_id | Integer PK | รหัสประจำตัวผู้ใช้งานระบบ |
| username | Varchar(50) | ชื่อผู้ใช้งานสำหรับ Login |
| **password** | Varchar(255) | รหัสผ่านที่ผ่านการเข้ารหัส |
| role | Varchar(20) | บทบาทผู้ใช้ |

**ของจริง** ตารางชื่อ `profiles` และ **ไม่มีคอลัมน์ password** — รหัสผ่านอยู่ใน
`auth.users` ซึ่งเป็นสคีมาที่ Supabase Auth ดูแลเอง (แฮชด้วย bcrypt) แอปเข้าถึงไม่ได้
และไม่ควรเข้าถึง `profiles.id` เป็น `uuid` ที่อ้างอิง `auth.users(id)` แบบ
`on delete cascade` ส่วน `role` เป็น enum `user_role` ที่มีสามค่า
(`admin` / `data_manager` / `member`) ไม่ใช่ varchar

**แก้เป็น** ใช้ตารางในไฟล์ `2026-09-08-data-dictionary.md` ข้อ 1 และเพิ่มหมายเหตุใต้ตาราง:

> หมายเหตุ: ระบบไม่เก็บรหัสผ่านไว้เอง การยืนยันตัวตนทั้งหมดจัดการโดย Supabase Auth
> ซึ่งเก็บรหัสผ่านที่ผ่านการแฮชไว้ในสคีมา `auth` แยกต่างหาก ตาราง `profiles`
> เก็บเฉพาะข้อมูลที่แอปพลิเคชันต้องใช้ (บทบาทและการตั้งค่า) และผูกกับผู้ใช้ผ่าน `id`
> ที่เป็นค่าเดียวกับ `auth.users.id` การออกแบบเช่นนี้ลดความเสี่ยงด้านความปลอดภัย
> เพราะรหัสผ่านไม่เคยผ่านโค้ดของโครงงานเลย

**เพราะอะไร** ข้อนี้กรรมการถามได้ตรงๆ ว่า "แฮชด้วยอะไร" แล้วคำตอบที่ถูกคือ
"ไม่ได้แฮชเอง" ซึ่งเป็นคำตอบที่ดีกว่า — แต่ต้องเขียนไว้ในเล่มก่อน

### 8. ตัด `profile_rating` ออกจากตารางที่ 3-10

**เล่มเขียนว่า** `Processed_Insights.profile_rating` — Integer — "คะแนนศักยภาพโปรไฟล์ (0-100)"

**ของจริง** ตาราง `analyses` เก็บ `score` ที่ผูกกับ `requirement_hash` เสมอ คือ
**"เหมาะกับความต้องการชุดนี้กี่คะแนน"** ไม่เคยมีคะแนนที่ลอยอยู่เดี่ยวๆ แบบ
"คนนี้ได้ 82 เต็ม 100"

**แก้เป็น** ลบแถว `profile_rating` ออกจากตาราง แล้วเพิ่มหมายเหตุใต้ตาราง `analyses`
ใน Data Dictionary ชุดใหม่:

> ระบบ**ไม่ให้คะแนนศักยภาพแบบลอยตัว**แก่ผู้สมัคร คะแนนทุกค่าในตารางนี้ผูกกับ
> `requirement_hash` ซึ่งเป็นค่าแฮชของข้อความความต้องการที่ใช้เปรียบเทียบ คะแนนจึงมี
> ความหมายว่า "เหมาะกับความต้องการชุดนี้เพียงใด" เท่านั้น ไม่ใช่การจัดอันดับคุณค่าของบุคคล

**เพราะอะไร** สามเหตุผล เรียงจากหนักไปเบา

1. **ตัวเลขไม่นิ่ง** วัดเมื่อ 2026-09-08: ข้อมูลเข้าชุดเดียวกัน โมเดลเดียวกัน รันซ้ำ
   ได้คะแนนต่างกันได้ถึง **10 แต้ม** คะแนนลอยตัวจึงเป็นตัวเลขที่ให้ความรู้สึกแม่นยำ
   เกินกว่าที่มันเป็นจริง
2. **ขัดกับข้อกำหนดการใช้งานของระบบเอง** ข้อ 4 ของ `/terms` และข้อ 3 ของ `/privacy`
   ห้ามใช้คะแนน AI ตัดสินบุคคลโดยลำพัง คะแนนที่ไม่ผูกกับตำแหน่งงานคือคะแนนที่
   ถูกใช้ผิดวิธีได้ง่ายที่สุด
3. **เป็นการตัดสินใจเชิงออกแบบที่อธิบายได้ดีในเล่ม** — ไม่ใช่ฟีเจอร์ที่ทำไม่ทัน
   แต่เป็นฟีเจอร์ที่จงใจไม่ทำ ควรเขียนเหตุผลไว้ในบทที่ 3 ด้วย

### 9. รวม Bookmark กับ Grouplist เป็นเรื่องเดียว (ตารางที่ 3-13, 3-14, 3-15 + 3.4.6, 3.4.8)

**เล่มเขียนว่า** สามตาราง — `Bookmarks` (บันทึกเดี่ยว), `Grouplists` (กลุ่ม),
`Group_Member` (สมาชิกในกลุ่ม) และ Activity Diagram แยกกันสองอัน (3.4.6 กับ 3.4.8)

**ของจริง** สองตาราง — `shortlists` (id, name, owner_id, created_at) และ
`shortlist_candidates` (shortlist_id, candidate_id, note) โดย **shortlist มีชื่ออยู่ในตัว
จึงทำหน้าที่ทั้ง Bookmark และ Grouplist พร้อมกัน**: ผู้ใช้สร้าง shortlist ชื่ออะไรก็ได้
แล้วหย่อนผู้สมัครเข้าไป จะมีอันเดียวชื่อ "สนใจ" (= bookmark) หรือหลายอันแยกตามตำแหน่งงาน
(= grouplist) ก็ได้ และเพิ่ม `note` ต่อผู้สมัครหนึ่งคนในหนึ่ง shortlist ได้ด้วย
ซึ่งเล่มไม่ได้ออกแบบไว้

**แก้เป็น**

1. ลบตารางที่ 3-13, 3-14, 3-15 ทิ้งทั้งสามตาราง แทนด้วยสองตาราง `shortlists` /
   `shortlist_candidates` จาก Data Dictionary ชุดใหม่
2. รวม **3.4.6** ("Dashboard และบุ๊กมาร์ก") กับ **3.4.8** ("การสร้าง Grouplist")
   เป็น Activity Diagram อันเดียว ชื่อ "3.4.6 Activity Diagram การจัดการ Shortlist"
   แล้วเลื่อนเลข 3.4.7 → 3.4.7 (คงเดิม) และลบ 3.4.8
3. เพิ่มย่อหน้าอธิบายเหตุผลใต้ตาราง:

> การออกแบบเดิมแยก "การบันทึกโปรไฟล์" (Bookmark) ออกจาก "การจัดกลุ่มโปรไฟล์"
> (Grouplist) เป็นสองระบบ แต่เมื่อพิจารณาแล้วพบว่า Bookmark คือ Grouplist ที่มีเพียง
> กลุ่มเดียว การรวมเป็นระบบเดียวจึงลดจำนวนตารางจากสามเหลือสอง ลดจำนวนหน้าจอที่
> ผู้ใช้ต้องเรียนรู้ และทำให้ผู้ใช้ไม่ต้องตัดสินใจตั้งแต่ต้นว่าโปรไฟล์ที่สนใจควรถูก
> "บันทึก" หรือ "จัดกลุ่ม" ซึ่งเป็นการตัดสินใจที่ไม่มีคำตอบถูก

**เพราะอะไร** นี่เป็นข้อที่ **เขียนแล้วได้เปรียบ** — การลดสามตารางเหลือสองพร้อมเหตุผล
คือหลักฐานว่าเกิดการออกแบบขึ้นจริงระหว่างทาง ไม่ใช่แค่ทำตามที่ร่างไว้

### 10. เขียน Use case 4 ใหม่ (หัวข้อ 3.3 และ 3.4.4)

**เล่มเขียนว่า** "การสั่ง AI วิเคราะห์ข้อมูล" — ผู้ใช้ใส่คำสั่งอิสระให้ AI ทำตาม
(Activity Diagram 3.4.4 "การสั่ง AI วิเคราะห์ข้อมูล")

**ของจริง** ผู้ใช้เปิดหน้าโปรไฟล์ผู้สมัครหนึ่งคน กรอก**ความต้องการของตำแหน่งงาน**
ลงในช่อง "ประเมินความเหมาะสม" แล้วกดประเมิน ระบบส่งข้อมูลผู้สมัคร + ข้อความความต้องการ
ไปให้ Gemini แล้วได้ **คะแนน 0-100 พร้อมเหตุผลภาษาไทย** กลับมา ผลถูก cache ไว้ใน
ตาราง `analyses` ตาม `requirement_hash` ถ้าประเมินด้วยความต้องการเดิมซ้ำจะได้ผลเดิม
โดยไม่เสียค่าเรียก AI อีกครั้ง

**แก้เป็น** เปลี่ยนชื่อ Use case และ Activity Diagram เป็น
**"การประเมินความเหมาะสมของผู้สมัครกับความต้องการของตำแหน่งงาน"** แล้วเขียน
Use case Description ใหม่ตามนี้:

| | |
|---|---|
| **ชื่อ** | ประเมินความเหมาะสมของผู้สมัคร |
| **ผู้กระทำ** | ผู้ใช้งานทั่วไป (member ขึ้นไป) |
| **เงื่อนไขก่อนเริ่ม** | ผู้ใช้ล็อกอินแล้ว และเปิดหน้ารายละเอียดผู้สมัครอยู่ |
| **ขั้นตอนผู้ใช้** | 1. เปิดหน้ารายละเอียดผู้สมัคร<br>2. กรอกความต้องการของตำแหน่งงานในช่อง "ประเมินความเหมาะสม" (หรือใช้ค่าตั้งต้นจากหน้าตั้งค่า)<br>3. กดปุ่มประเมิน<br>4. อ่านคะแนนและเหตุผล |
| **ขั้นตอนระบบ** | 4.1 ตรวจสอบสิทธิ์การเข้าถึง<br>4.2 คำนวณค่าแฮชของข้อความความต้องการ<br>4.3 ตรวจว่ามีผลที่เคยประเมินไว้แล้วหรือไม่ ถ้ามีให้คืนผลเดิม<br>4.4 ถ้ายังไม่มี ส่งข้อมูลผู้สมัครและความต้องการไปยัง Google Gemini<br>4.5 รับคะแนน 0-100 และเหตุผลภาษาไทยกลับมา<br>4.6 บันทึกผลลงตาราง `analyses` เพื่อใช้ซ้ำ<br>4.7 แสดงผลบนหน้าจอ |
| **เงื่อนไขหลังจบ** | ผลการประเมินถูกบันทึกและแสดงต่อผู้ใช้ |
| **กรณียกเว้น** | หากบริการ AI ไม่ตอบสนองภายในเวลาที่กำหนด ระบบแจ้งผู้ใช้ให้ลองใหม่ โดยไม่บันทึกผลที่ไม่สมบูรณ์ |

**เพราะอะไรถึงไม่ทำแบบเดิม** ช่องคำสั่งอิสระให้ AI มีปัญหาสามอย่างที่แก้ไม่ได้ในระดับ
โครงงาน: (1) ควบคุมผลลัพธ์ไม่ได้ ผู้ใช้พิมพ์อะไรก็ได้แล้วได้อะไรก็ได้กลับมา
ทดสอบและเขียน UAT ไม่ได้ (2) เปิดช่องให้ **prompt injection** — ผู้ใช้พิมพ์คำสั่ง
ให้ AI เพิกเฉยกฎเดิมได้ (3) ค่าเรียก AI คาดเดาไม่ได้ ขณะที่รูปแบบปัจจุบันมี
`requirement_hash` ทำให้ cache ได้และคุมค่าใช้จ่ายได้

### 12. เพิ่มฟีเจอร์ประเมินตัวเอง (Self-assessment) เข้าขอบเขต

**ของจริง** ระบบมีฟีเจอร์ที่เล่มไม่ได้พูดถึงเลย: ผู้ใช้อัปโหลด resume PDF ของตัวเอง
(หรือกรอกข้อมูลเอง) ระบบอ่าน PDF ด้วย Gemini แบบ multimodal สกัดเป็นร่างข้อมูล
**ให้ผู้ใช้ตรวจและยืนยันก่อน** แล้วจึงวิเคราะห์เป็นจุดแข็ง/จุดที่ยังขาด/สิ่งที่ควรพัฒนา
และ**จัดอันดับตำแหน่งงานที่เหมาะกับโปรไฟล์นั้น** ข้อมูลเก็บในตาราง `self_profiles`
ซึ่ง**แยกจากตาราง `candidates` โดยสิ้นเชิง** — ข้อมูลที่ผู้ใช้อัปโหลดเองจะไม่มีวัน
ไปโผล่ในการค้นหาของฝ่ายบุคคล

**แก้เป็น** เพิ่มหัวข้อใหม่ **1.3.1.5 การประเมินตัวเอง (Self-assessment)** ต่อจาก 1.3.1.4:

> **1.3.1.5 การประเมินตัวเอง (Self-assessment)**
>
> 1) ผู้ใช้สามารถอัปโหลดไฟล์ Resume/CV ของตนเอง (PDF) เพื่อให้ระบบสกัดข้อมูลอัตโนมัติ
> 2) ผู้ใช้สามารถ**ตรวจสอบและแก้ไขข้อมูลที่ระบบสกัดได้ก่อนบันทึก** ทุกครั้ง
> 3) ผู้ใช้สามารถกรอกข้อมูลด้วยตนเองโดยไม่ต้องอัปโหลดไฟล์
> 4) ผู้ใช้สามารถดูผลวิเคราะห์จุดแข็ง จุดที่ยังขาด และสิ่งที่ควรพัฒนา
> 5) ผู้ใช้สามารถดูรายการตำแหน่งงานที่เหมาะกับโปรไฟล์ของตน เรียงตามความเหมาะสม

และเพิ่มใน **1.3.2** ขอบเขต Back-end เป็นหัวข้อ **1.3.2.5**:

> **1.3.2.5 การประมวลผลไฟล์ Resume ของผู้ใช้**
>
> 1) ระบบสามารถอ่านไฟล์ PDF ด้วยโมเดล AI แบบ Multimodal โดยไม่ต้องใช้ไลบรารีแปลง
>    ข้อความ จึงรองรับไฟล์ที่สแกนมาเป็นภาพได้
> 2) ระบบแยกขั้นตอน "สกัดข้อเท็จจริง" ออกจาก "การประเมิน" เป็นสองคำสั่ง เพื่อให้
>    ประเมินซ้ำได้โดยไม่ต้องอัปโหลดไฟล์ใหม่
> 3) ระบบไม่บันทึกข้อมูลใดจนกว่าผู้ใช้จะยืนยันร่างข้อมูลด้วยตนเอง
> 4) ระบบจัดเก็บข้อมูลที่ผู้ใช้อัปโหลดในตารางแยกจากฐานข้อมูลผู้สมัคร และจำกัดการเข้าถึง
>    ให้เจ้าของข้อมูลเท่านั้น

พร้อมเพิ่ม **Use case ใหม่** ในหัวข้อ 3.2/3.3 และ **Activity Diagram 3.4.9**
"การประเมินตัวเองจากไฟล์ Resume"

**เพราะอะไร** นี่คือฟีเจอร์ที่ทำเสร็จแล้วและใช้เทคนิคที่ยากที่สุดในโครงงาน

### 13. เพิ่มหัวข้อการคุ้มครองข้อมูลส่วนบุคคล (PDPA)

**ของจริง** ระบบมีกลไก PDPA ที่ทำงานอยู่จริง ซึ่งเล่มไม่ได้พูดถึงเลยแม้แต่คำเดียว
ทั้งที่โครงงานนี้เก็บข้อมูลบุคคลจากแหล่งสาธารณะ:

| กลไก | ทำอะไร |
|---|---|
| ตาราง `ingest_runs` | บันทึกว่าข้อมูลชุดไหนเข้าระบบเมื่อไร จากแหล่งใด — เป็นหลักฐานที่มาของข้อมูล |
| ตาราง `pending_candidates` | ข้อมูลที่ไม่ครบเกณฑ์เข้าคิวรอมนุษย์ตรวจก่อน ไม่เข้าฐานข้อมูลอัตโนมัติ |
| ตาราง `suppressed_profiles` | รายชื่อผู้ที่ขอให้ลบข้อมูล ระบบตรวจรายชื่อนี้**ก่อน**นำเข้าทุกครั้ง จึงไม่มีทางถูกดึงกลับเข้ามาใหม่ |
| ตาราง `activity_log` | บันทึกว่าใครทำอะไรกับข้อมูลเมื่อไร |
| หน้า `/terms` และ `/privacy` | ประกาศเงื่อนไขการใช้งานและนโยบายความเป็นส่วนตัว ระบุผู้ประมวลผลภายนอกทั้งสามราย (Supabase, Gemini, Vercel) ซึ่งอยู่นอกประเทศไทย จึงเป็นการโอนข้อมูลข้ามพรมแดนที่ต้องแจ้ง |
| ข้อกำหนดในการใช้คะแนน | ข้อ 4 ของ `/terms` และข้อ 3 ของ `/privacy` ห้ามใช้คะแนน AI ตัดสินบุคคลโดยลำพัง |
| ระดับสิทธิ์ 3 ระดับ | `admin` / `data_manager` / `member` — ผู้ใช้ทั่วไปนำเข้าหรือแก้ไขข้อมูลผู้สมัครไม่ได้ |
| การจำกัดคอลัมน์ | ผู้ใช้ที่ล็อกอินอ่าน `candidates` ผ่านคีย์สาธารณะได้เพียง 3 คอลัมน์ (id, ชื่อ, headline) อีเมลและข้อมูลติดต่ออ่านผ่านเซิร์ฟเวอร์เท่านั้น |

**แก้เป็น** เพิ่มหัวข้อ **2.6 การคุ้มครองข้อมูลส่วนบุคคล (PDPA)** ในบทที่ 2 อธิบาย
พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 โดยเน้นสามมาตราที่เกี่ยวกับโครงงานนี้ตรงๆ
(ฐานประโยชน์อันชอบธรรม, สิทธิของเจ้าของข้อมูล, หน้าที่แจ้งเมื่อเก็บจากแหล่งอื่น)
แล้วเพิ่มหัวข้อ **3.8 การออกแบบด้านการคุ้มครองข้อมูลส่วนบุคคล** ในบทที่ 3
อธิบายตารางข้างบนว่ากลไกไหนรองรับข้อกำหนดข้อใด

**ต้องเขียนข้อจำกัดไว้ด้วยอย่างตรงไปตรงมา** (จะเป็นหัวข้อ "ข้อจำกัดและงานในอนาคต"
ในบทที่ 5 ก็ได้):

> การเผยแพร่นโยบายความเป็นส่วนตัวบนเว็บไซต์ยังไม่ครบถ้วนตามมาตรา 25 แห่ง พ.ร.บ.
> คุ้มครองข้อมูลส่วนบุคคล ซึ่งกำหนดให้ต้อง**แจ้งเจ้าของข้อมูล**เมื่อเก็บข้อมูลจาก
> แหล่งอื่นที่ไม่ใช่เจ้าของข้อมูลโดยตรง เนื่องจากผู้สมัครที่ข้อมูลถูกเก็บมาจาก
> แหล่งสาธารณะจะไม่ได้เข้ามาอ่านหน้านโยบายนี้ด้วยตนเอง การมีหน้าเว็บจึงเป็นเพียง
> ส่วนหนึ่งของการปฏิบัติหน้าที่ ไม่ใช่ทั้งหมด นอกจากนี้เอกสารทางกฎหมายทั้งสองฉบับ
> ยังไม่ผ่านการตรวจสอบโดยผู้มีคุณสมบัติทางกฎหมาย

**เพราะอะไร** โครงงานที่เก็บข้อมูลบุคคลจากแหล่งสาธารณะแล้วไม่พูดถึง PDPA เลย
คือคำถามแรกที่กรรมการจะถาม การมีคำตอบเตรียมไว้พร้อมยอมรับข้อจำกัดอย่างตรงไปตรงมา
ดีกว่าถูกถามแล้วตอบไม่ได้มาก
