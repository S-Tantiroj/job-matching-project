# v3.1 — ประเมินตัวเอง: แทรกขั้นตอนตรวจข้อมูล และเพิ่มทางกรอกเอง

**เป้าหมาย:** เปลี่ยน flow ประเมินตัวเองจาก "อัปโหลดแล้ว AI ตัดสินให้เลย" เป็น
"อัปโหลด → ตรวจสิ่งที่ AI อ่านได้ → ยืนยันแล้วจึงวิเคราะห์" พร้อมเปิดทางที่สองให้คน
ที่ไม่มีไฟล์ CV กรอกข้อมูลเองได้

**สถาปัตยกรรมโดยรวม:** ผ่า `POST /api/self-assessment` เดิมที่ทำสามอย่างรวดในคำขอเดียว
ออกเป็นสองเฟส เฟสแรกอ่าน PDF แล้วคืน draft กลับเบราว์เซอร์โดยไม่เขียนฐานข้อมูล
เฟสสองรับ draft ที่ผู้ใช้ยืนยันแล้วไปวิเคราะห์ ทำ embedding และบันทึก ฟอร์มที่ใช้ตรวจ
draft กับฟอร์มกรอกเองเป็นตัวเดียวกัน ต่างกันแค่ค่าเริ่มต้น

**Stack:** เหมือนเดิมทั้งหมด ไม่มี dependency ใหม่ ไม่มี migration ใหม่

---

## ขอบเขต

**อยู่ในรอบนี้:**

1. `POST /api/self-assessment/parse` — PDF → draft, ไม่เขียนฐานข้อมูล
2. `POST /api/self-assessment` — เปลี่ยน body จาก FormData เป็น JSON ของ draft ที่ยืนยันแล้ว
3. `lib/self/profileDraft.ts` — type + การตรวจและทำให้เป็นมาตรฐาน (ฟังก์ชันบริสุทธิ์)
4. ฟอร์มเดียวใช้ทั้งตรวจ draft และกรอกเอง + หน้าเลือกทางเข้าสองทาง
5. ปรับ prompt: เพิ่ม `industry`, เลิกขอ `raw_text`, จำกัด 10 รายการ, กันข้อมูลอ่อนไหว
6. ปรับ `assessProfile`: ส่งจำนวนปีประสบการณ์ที่คำนวณแล้วเข้า prompt

**ไม่อยู่ในขอบเขต:**

- รับไฟล์ใหญ่เกิน 4MB (ต้องอัปโหลดตรงเข้า Supabase Storage — งานคนละก้อน)
- บันทึกร่างอัตโนมัติในเบราว์เซอร์ (พิจารณาแล้วไม่เอา ดูหัวข้อ "ทางเลือกที่ตัดออก")
- draft ที่เก็บในฐานข้อมูลพร้อมสถานะ (พิจารณาแล้วไม่เอา)
- แบ่งฟอร์มเป็นหลายขั้น (wizard)
- รับไฟล์ชนิดอื่นนอกจาก PDF

## ปัญหาของ flow เดิม

`POST /api/self-assessment` ปัจจุบันทำสามอย่างในคำขอเดียวแล้วค่อย insert:

```
parsePdfProfile  →  assessProfile  →  embedText  →  insert
```

**ถ้าขั้นไหนล้ม ไม่เขียนอะไรเลย** ซึ่งถูกต้องในแง่ที่ว่าโปรไฟล์ที่ไม่มี embedding จะ
กลายเป็นข้อมูลเสียแบบเงียบ แต่ผลข้างเคียงคือ **Gemini อ่าน PDF สำเร็จแล้ว — ซึ่งเป็นขั้น
ที่ช้าและแพงที่สุด — แล้ว `assessProfile` เจอ 503 งานที่สำเร็จถูกทิ้งทั้งหมด** ผู้ใช้ต้อง
อัปโหลดใหม่ตั้งแต่ต้น

ปัญหาที่สอง: ผู้ใช้ไม่เคยเห็นสิ่งที่ AI เข้าใจ บทวิเคราะห์และอันดับงานทั้งหมดสร้างจาก
`parsed_data` ถ้าตรงนั้นอ่านมาผิด ผู้ใช้จะเห็นคำแนะนำที่ดูน่าเชื่อแต่ตั้งอยู่บนประวัติที่ไม่ใช่
ของตัวเอง โดยไม่มีทางรู้ว่าผิดตรงไหน — และ CV ยิ่งยาว โอกาสอ่านสลับยิ่งสูง

ปัญหาที่สาม: คนที่ไม่มีไฟล์ CV — นักศึกษาจบใหม่ หรือคนที่ประวัติอยู่ใน Google Docs —
ใช้ฟีเจอร์นี้ไม่ได้เลย ไม่มีทางเข้าอื่น

## การตัดสินใจและเหตุผล

### 1. ตรวจ template ทุกครั้ง ไม่ใช่เฉพาะตอนอ่านพลาด

ทางเลือกอื่นคือวิเคราะห์ให้เลยแล้วมีปุ่มแก้ทีหลัง หรือให้ตรวจเฉพาะตอนข้อมูลไม่ครบ
เลือกตรวจทุกครั้งเพราะ **ทุกอย่างที่ผู้ใช้เห็นสร้างจาก `parsed_data`** การให้ตรวจหลัง
วิเคราะห์แล้วแปลว่าผู้ใช้อ่านคำแนะนำที่อาจผิดไปแล้วหนึ่งรอบ ส่วน "ตรวจเฉพาะตอนไม่ครบ"
ต้องนิยามคำว่าไม่ครบ ซึ่งจับไม่ได้กรณีที่อันตรายที่สุดคือ **ข้อมูลครบแต่ผิด** (สลับปี
รวมสองบริษัทเป็นอันเดียว)

ราคาที่จ่ายคือคลิกเพิ่มหนึ่งครั้งสำหรับทุกคน รับได้เพราะยังถูกกว่าการรอ AI วิเคราะห์ใหม่

### 2. draft อยู่ในเบราว์เซอร์ ไม่เขียนฐานข้อมูลจนกว่าจะยืนยัน

ทางเลือกอื่นคือเขียน draft ลงฐานทันทีพร้อมคอลัมน์สถานะ ซึ่งทำให้ปิดแท็บแล้วกลับมาทำต่อได้

เลือกไม่เขียน เพราะแถวใน `self_profiles` คือข้อมูลส่วนบุคคลที่มีอายุเก็บ 1 ปีตาม
`lib/legal/meta.ts` **การเขียนประวัติฉบับที่ AI อ่านมาผิดลงฐานก่อนที่เจ้าตัวจะรับรอง
คือสิ่งที่ขั้นตอนตรวจสอบนี้ตั้งใจป้องกันตั้งแต่แรก** และยังต้องมีทางเก็บกวาด draft ที่ถูกทิ้ง
กับ migration ใหม่ ซึ่งเป็นความซับซ้อนที่แลกมาด้วยกรณีเดียวคือปิดแท็บกลางคัน

ทางนี้ยังได้เรื่องกู้คืนมาเกือบครบ — ถ้า `assessProfile` ล้ม ฟอร์มยังอยู่ครบบนหน้าจอ
กดวิเคราะห์ซ้ำได้โดยไม่ต้องอ่าน PDF ใหม่

### 3. จำกัดจำนวนรายการตอนอ่านไฟล์ ไม่ทำ autosave

CV ที่ยาวทำให้ฟอร์มยาวตามและเสี่ยงเสียงานถ้าปิดแท็บ เลือกแก้ที่ต้นเหตุ (ฟอร์มสั้นตั้งแต่แรก)
แทนการแก้ที่อาการ (บันทึกร่างอัตโนมัติ) เพราะ 10 รายการล่าสุดพอสำหรับการจับคู่งาน —
ตำแหน่งเมื่อ 20 ปีก่อนแทบไม่มีน้ำหนักใน embedding อยู่แล้ว — และการเก็บร่างใน
localStorage ก็มีปัญหาความเป็นส่วนตัวของตัวเองบนเครื่องที่ใช้ร่วมกัน

**ผลที่ยอมรับ:** ปิดแท็บกลางคันแล้วต้องอัปโหลดใหม่ เสียการเรียกอ่าน PDF หนึ่งครั้ง

**ไม่แสดงจำนวนที่ถูกตัด** เช่น "แสดง 10 จาก 24" เพราะเป็นตัวเลขที่โมเดลบอกมาและเรา
ตรวจสอบไม่ได้ การขึ้นตัวเลขผิดแย่กว่าไม่ขึ้นเลย ใช้ข้อความว่า "แสดงเฉพาะรายการล่าสุด
ถ้าขาดอะไรสำคัญเพิ่มเองได้" แทน

### 4. สองทางเข้าตั้งแต่หน้าแรก

"อัปโหลด PDF" กับ "กรอกข้อมูลด้วยตัวเอง" คู่กัน ไม่ใช่ให้ทางกรอกเองโผล่เฉพาะตอน
อัปโหลดล้มเหลว เพราะคนที่ไม่มีไฟล์เลยจะต้องแกล้งอัปโหลดอะไรสักอย่างให้พังก่อนถึงจะเจอ
ทางที่ใช้ได้ ซึ่งไม่มีใครเดาออก

ต้นทุนเพิ่มเกือบเป็นศูนย์ เพราะฟอร์มเป็นตัวเดียวกับที่ใช้ตรวจ draft อยู่แล้ว

### 5. เลิกเก็บ `raw_text`

`raw_text` ถูกเขียนลง `self_profiles` แต่ **grep ทั้งรีโปแล้วไม่มีที่ไหนอ่านเลย** —
ไม่ใช่ `assessProfile` ไม่ใช่ `matchJobsForProfile` ไม่ใช่หน้า `/self-assessment`
ทั้งหมดใช้แค่ `parsed_data`

มันเป็น output token ซึ่งเป็นฝั่งที่แพงที่สุด และเป็นการสั่งให้โมเดลพิมพ์เอกสารทั้งฉบับ
กลับมาเก็บไว้เฉยๆ CV 10 หน้าคือหลายพัน token ทั้งค่าเงินและเวลารอ

ข้อแก้ตัวเดิมของมันคือเป็นร่องรอยว่าโมเดลอ่านอะไรไป แต่**พอผู้ใช้กลายเป็นคนตรวจและ
รับรองข้อมูลเองทุกครั้ง สิ่งที่อยู่ในฐานก็คือฉบับที่เจ้าตัวยืนยันแล้ว ร่องรอยนั้นจึงหมดความหมาย**
และการเก็บน้อยลงตรงกับหลักลดข้อมูลเท่าที่จำเป็นตาม PDPA ที่ประกาศไว้ในนโยบายอยู่แล้ว

**คอลัมน์ `raw_text` ยังคงอยู่ในตาราง** ตามกติกาว่า migration ต้อง additive เพียงแต่
ไม่เขียนค่าลงไปอีก แถวเก่าที่มีค่าอยู่แล้วไม่ถูกแตะ

## สถาปัตยกรรม

### เส้นทาง API

```
POST /api/self-assessment/parse      (ใหม่)
  รับ:  FormData { file: PDF }
  ทำ:   validateUpload → parsePdfProfile (Gemini ×1)
  คืน:  { draft: ProfileDraft }
  ไม่เขียนฐานข้อมูล

POST /api/self-assessment            (เดิม เปลี่ยน body)
  รับ:  JSON ProfileDraft ที่ผู้ใช้ยืนยันแล้ว
  ทำ:   validateProfileDraft → assessProfile (×1) → embedText (×1) → insert
  คืน:  { id }
```

ทางกรอกเองยิงเข้า route ที่สองตรงๆ โดยไม่แตะ route แรก

### รูปร่างข้อมูล

`ProfileDraft` ต้องเข้ากันได้กับ `CandidateInput` เพื่อส่งเข้า `buildEmbedText` ได้ตรงๆ
บวกฟิลด์ `gpa` ต่อรายการการศึกษาซึ่ง `CandidateInput` ไม่มี

| กลุ่ม | ช่อง | เพดาน (บังคับฝั่งเซิร์ฟเวอร์) |
|---|---|---|
| ตัวตน | `full_name` **บังคับ** | 120 ตัวอักษร |
| | `headline` | 200 |
| | `industry` | 120 |
| | `location` | 120 |
| | `summary` | 2,000 |
| การศึกษา | สูงสุด **20** รายการ | |
| | `institution` | 200 |
| | `country` | 60 |
| | `degree` | 120 |
| | `field_of_study` | 120 |
| | `start_year` / `end_year` | จำนวนเต็ม 1900–2100 |
| | `gpa` | **string** 60 ตัวอักษร |
| ประสบการณ์ | สูงสุด **20** รายการ | |
| | `company` / `title` | 200 |
| | `start_date` / `end_date` | ISO `YYYY-MM-DD` หรือ null |
| | `description` | 1,000 |
| สกิล | สูงสุด 50 รายการ | ชิ้นละ 60 |

**เพดานของ prompt กับเพดานของเซิร์ฟเวอร์ไม่ใช่ตัวเดียวกัน โดยตั้งใจ** — prompt ขอ
**10 รายการล่าสุด** เพื่อให้ฟอร์มสั้น ส่วนเซิร์ฟเวอร์ยอมรับได้ถึง **20** เพราะเราบอกผู้ใช้ว่า
"ถ้าขาดอะไรสำคัญเพิ่มเองได้" ถ้าเพดานสองตัวเท่ากันที่ 10 คำเชิญนั้นจะเป็นคำโกหก —
ผู้ใช้กดเพิ่มแล้วโดนปฏิเสธทันที

**เพดานนับเป็น code point ไม่ใช่ตัวอักษรที่ตาเห็น** ภาษาไทยใช้หลาย code point ต่อ
หนึ่งตัวอักษรที่มองเห็น เช่น `"เกียรตินิยมอันดับหนึ่ง"` ยาว 22 code point ทั้งที่ดูสั้น
นี่คือเหตุผลที่ `gpa` ตั้งไว้ที่ 60 ไม่ใช่ 20 — เพดานที่ตั้งจากการนับด้วยตาจะตัดค่าที่ถูกต้องทิ้ง

`start_date` / `end_date` ต้องตรงรูป `YYYY-MM-DD` เท่านั้น ค่าที่ผิดรูปถูกปฏิเสธ
ไม่ใช่เดาให้ `end_date` เป็น null หมายถึงตำแหน่งปัจจุบัน ซึ่งเป็นความหมายเดียวกับที่
`computeYearsExperience` ใช้อยู่แล้ว

**ผลการเรียนเก็บเป็น string ไม่ใช่ number** เพราะสเกลไม่เหมือนกัน — 3.45 จากระบบ 4.0,
4.2 จากระบบ 5.0, "เกียรตินิยมอันดับหนึ่ง", "First Class Honours" ล้วนถูกต้อง การบังคับ
เป็นตัวเลขทำให้ค่าที่ถูกกรอกไม่ได้ และค่าที่กรอกได้ก็เทียบข้ามคนไม่ได้อยู่ดี

## ความปลอดภัย: route ยืนยันต้องไม่เชื่อ client

flow เดิมข้อมูลที่จะเขียนลงฐาน**มาจาก Gemini เท่านั้น** flow ใหม่ **เบราว์เซอร์เป็นคน
ส่ง JSON เข้ามา** ซึ่งเปิดพื้นที่ใหม่ที่เดิมไม่มี ใครก็ยิงตรงเข้า route ได้โดยไม่ผ่านฟอร์ม
เช่นส่ง `summary` ยาวสิบล้านตัวอักษรให้เราจ่ายค่า embedding แทน หรือส่ง experience
หมื่นรายการ

**เพดานทุกตัวในตารางข้างบนต้องบังคับใน `validateProfileDraft` ฝั่งเซิร์ฟเวอร์**
การจำกัดใน `<input maxLength>` เป็นเรื่องประสบการณ์ผู้ใช้ ไม่ใช่การป้องกัน

`validateProfileDraft` ต้อง:

- ปฏิเสธเมื่อไม่มี `full_name`
- ปฏิเสธพร้อมระบุชื่อช่องเมื่อเกินเพดาน (ไม่ตัดให้เงียบๆ — ผู้ใช้ต้องรู้ว่าอะไรหาย)
- **ตัดฟิลด์ที่ไม่รู้จักทิ้ง** ไม่ให้ไหลลงฐานผ่าน jsonb ซึ่งรับอะไรก็ได้
- คืนค่าที่ทำให้เป็นมาตรฐานแล้ว ไม่ใช่ค่าดิบ

route ยังคงใช้ service-role client และยังคงผูก `owner_id` จาก session เท่านั้น
ห้ามรับ `owner_id` จาก body

## ข้อมูลที่เข้าไปในการวิเคราะห์

### เพิ่ม `industry`

`buildEmbedText` ใส่ `industry` เข้า embedding และฝั่งงานมี `jobs.category` เป็น
คู่เทียบที่จงใจจัดให้ตรงกันใน `buildJobEmbedText` แต่ schema ใน `parsePdfProfile`
**ไม่มีฟิลด์นี้** โปรไฟล์ที่อัปโหลดจึงขาดสัญญาณที่ฝั่งงานเตรียมไว้ให้ เพิ่มทั้งใน prompt
และในฟอร์ม

### กันข้อมูลอ่อนไหวตั้งแต่ prompt

CV ไทยจำนวนมากมีวันเกิด ศาสนา สถานภาพสมรส ส่วนสูง-น้ำหนัก และรูปถ่ายติดมาตามธรรมเนียม
prompt ปัจจุบันไม่ได้ห้าม ข้อมูลพวกนี้จึงมีโอกาสถูกกวาดเข้า `summary`

**ศาสนาและข้อมูลสุขภาพเป็นข้อมูลอ่อนไหวตาม PDPA มาตรา 26 ซึ่งต้องขอความยินยอม
โดยชัดแจ้งแยกต่างหาก และเราไม่ได้ขอ** สั่งใน prompt ให้ข้ามทั้งหมด และไม่มีช่องเหล่านี้
ในฟอร์ม — ไม่ช่วยจับคู่งานอยู่แล้ว

### "แนะนำตัวเอง" ไม่บังคับ แต่ต้องเด่น

จาก `scripts/ablate-embedding.ts`: ตัด skills ออก Spearman เหลือ 0.951 แต่
**ตัด summary ออกเหลือ 0.856** — summary มีน้ำหนักในการจัดอันดับมากกว่า skills
คนที่กรอกเองแล้วข้ามช่องนี้จะได้ผลจับคู่งานแย่ลงชัดเจนโดยไม่รู้ตัว

จึงยังไม่บังคับ แต่วางไว้เด่น มีตัวอย่างสั้นกำกับ และถ้าเว้นว่างให้ขึ้นเตือนเบาๆ ก่อนกดวิเคราะห์

(ตัวเลขข้างบนวัดจากผู้สมัคร `source = 'synthetic'` 25 คน เป็นขอบบน ดู CLAUDE.md)

### คำนวณจำนวนปีประสบการณ์ส่งเข้า prompt

`assessProfile` ปัจจุบันได้แค่วันที่ดิบแล้วต้องบวกลบเอง ซึ่งโมเดลทำพลาดบ่อย
ใช้ `computeYearsExperience` ที่มีอยู่แล้วใน `lib/ingest/normalize.ts` คำนวณก่อน
แล้วส่งเป็นตัวเลขสำเร็จเข้า prompt พร้อมกับ `gpa` ที่ฟอร์มเก็บมา

### ฟิลด์ที่ไม่ช่วยการจัดอันดับ (แต่ยังเก็บ)

`description` ของประสบการณ์ และ `field_of_study` **ไม่อยู่ใน `buildEmbedText`** —
embedding ใช้แค่ `title company` และ `degree institution country` สองฟิลด์นี้ช่วยเฉพาะ
บทวิเคราะห์ ยังเก็บเพราะบทวิเคราะห์คือสิ่งที่ผู้ใช้อ่าน แต่เป็นเหตุผลว่าทำไมเพดาน
1,000 ตัวอักษรถึงไม่ทำร้ายใคร

### `gpa` ไม่เข้า embedding

สองเหตุผล: ตัวเลขที่ไม่มีสเกลกำกับเป็นสัญญาณรบกวนในเวกเตอร์เชิงความหมาย และที่สำคัญกว่า —
**`buildEmbedText` ใช้ร่วมกับฝั่งผู้สมัคร การแตะมันทำให้ `embed_hash` ของทั้งตาราง
`candidates` เปลี่ยน แล้วต้อง re-embed ใหม่ทั้งหมด** `gpa` จึงไปอยู่สองที่: แสดงบน
หน้าจอ และป้อนเข้า prompt ของ `assessProfile`

## เทียบกับ flow เดิม

### จำนวนการเรียก Gemini

| สถานการณ์ | เดิม | ใหม่ |
|---|---|---|
| อัปโหลดสำเร็จจนจบ | 3 | 3 |
| กรอกเอง | ทำไม่ได้ | **2** |
| วิเคราะห์ล้มแล้วลองใหม่ | 3 ใหม่ทั้งหมด | **2** |
| ตรวจแล้วเปลี่ยนใจ ปิดทิ้ง | ไม่มีจุดนี้ | **1 ที่จ่ายแล้วไม่ได้อะไร** |

แถวสุดท้ายเป็นต้นทุนใหม่ที่ flow เดิมไม่มี บันทึกไว้ให้ครบ

### ต้นทุนต่อการอ่าน PDF หนึ่งครั้ง

ลดลงจากการตัด `raw_text` และจำกัด 10 รายการ resume 2 หน้าประหยัด output ราว
700–1,000 token · CV 10 หน้าราว 4,000–6,000 token คิดเป็นเงินราว $0.003–$0.023
ต่อครั้งที่ราคา output ปัจจุบัน

**ตัวเลขนี้เป็นการประมาณ ไม่ใช่ค่าที่วัดแล้ว** — วัดจริงได้ด้วยการอ่าน `usageMetadata`
จาก response เหมือนที่ `scripts/check-gemini-tier.ts` ทำ ควรทำตอน implement

### ความเร็วที่ผู้ใช้รู้สึก

**flow ใหม่ช้าลง ไม่ใช่เร็วขึ้น** เดิมรอครั้งเดียว 10–20 วินาทีแล้วจบ ใหม่คือรอสั้นลง →
นั่งตรวจ (เวลาคน) → รออีกรอบ เวลารวมจนได้บทวิเคราะห์ยาวขึ้นแน่นอน

ถ้าเป้าหมายคือความเร็ว flow นี้ตอบไม่ได้ สิ่งที่มันซื้อคือ:

- ข้อมูลที่ผู้ใช้รับรองแล้ว แทนข้อมูลที่ AI เดา
- เลิกทิ้งงานที่สำเร็จแล้วเมื่อขั้นถัดไปล้ม
- ทางเข้าสำหรับคนที่ไม่มีไฟล์ ซึ่งเดิมใช้ฟีเจอร์นี้ไม่ได้เลย
- เก็บข้อมูลส่วนบุคคลน้อยลง
