# หน้าสาธารณะ — หน้าแนะนำฟีเจอร์ และหน้าคู่มือ/UAT

วันที่ 2026-08-29

## ปัญหาที่แก้

ตอนนี้คนที่เปิด `skouth` โดยไม่มีบัญชีเห็นเพียงชื่อระบบกับปุ่มเข้าสู่ระบบ ไม่มีอะไร
อธิบายว่าระบบทำอะไรได้ และไม่มีคู่มือให้ผู้ใช้หรือผู้ทดสอบอ่าน

งานนี้เพิ่มสองหน้าสาธารณะ — หน้าแนะนำฟีเจอร์ที่ `/` และหน้าคู่มือที่ `/help` ซึ่งมี
ทั้งคู่มือผู้ใช้ ตารางทดสอบการยอมรับ ไฟล์ PDF ให้ดาวน์โหลด และช่องทางติดต่อ

## ขอบเขต

ในขอบเขต — สองหน้าข้างต้น ไฟล์ PDF หนึ่งไฟล์ ลิงก์คู่มือใน nav ของแอป และคลาส CSS
ที่จำเป็น

นอกขอบเขต — ไม่มี migration ไม่แตะ `middleware.ts` ไม่แตะกลุ่ม `(auth)` ไม่แตะ
ตรรกะการค้นหา การนำเข้า หรือการให้คะแนนใดๆ ไม่มีระบบเก็บคำขอทดลองใช้

## การตัดสินใจที่กำหนดรูปร่างงานนี้

### กลุ่มผู้อ่านคือคนภายนอก แต่ปุ่มไม่ใช่ "สมัครสมาชิก"

ระบบนี้เก็บข้อมูลส่วนบุคคลจริงของคนไทยที่ scrape มา ปุ่มสมัครที่เปิดให้ใครก็กดได้
จะทำให้คนนอกเข้าถึงฐานข้อมูลผู้สมัครทั้งหมดทันทีที่ยืนยันอีเมล หน้าแรกจึงเป็น
**หน้าแนะนำ ไม่ใช่ประตูเข้าระบบ** ปุ่มหลักพาไปหน้าคู่มือและช่องทางติดต่อแทน

`/signup` ยังเปิดอยู่ตามเดิม งานนี้ไม่ได้ปิดมัน เพียงแต่ไม่โฆษณา — การปิดจริงต้อง
ทำที่ Supabase (ดูหัวข้อ "Not done" ใน CLAUDE.md) ไม่ใช่ที่หน้าเว็บ

### เนื้อหาเว็บกับ PDF แยกกันโดยตั้งใจ

เจ้าของงานเลือกให้หน้า `/help` กับไฟล์ PDF เป็นเนื้อหาสองชุดที่ดูแลแยกกัน
แลกความเสี่ยงเรื่องความไม่ตรงกันกับอิสระในการจัดหน้า PDF ได้เต็มที่

ตัวลดความเสี่ยงคือ **การประทับเวอร์ชัน** ไม่ใช่การรวมแหล่ง — `lib/help/docMeta.ts`
เก็บเวอร์ชันและวันที่ แสดงบนหน้าเว็บข้างปุ่มดาวน์โหลด และพิมพ์บนหน้าปก PDF ด้วย
ความไม่ตรงกันจึงมองเห็นได้ในหนึ่งวินาทีแทนที่จะเงียบจนมีคนถือเอกสารผิดเวอร์ชัน
ไปทดสอบ

### ไม่ฝัง PDF viewer ในหน้า

`<iframe>` ที่ชี้ไปไฟล์ PDF แสดงผลไม่ได้บนเบราว์เซอร์มือถือหลายตัว บางตัวดาวน์โหลด
ทับแทนการแสดง และเนื้อหาในนั้นซ้ำกับที่อยู่บนหน้าอยู่แล้ว จึงใช้ปุ่ม "เปิดในแท็บใหม่"
ซึ่งให้ผลเท่ากันและพังยากกว่า

## สถาปัตยกรรม

### เส้นทาง

สร้าง route group `(public)` ใหม่

```
app/(public)/layout.tsx      nav เบาสำหรับหน้าสาธารณะ
app/(public)/page.tsx        /       หน้าแนะนำฟีเจอร์
app/(public)/help/page.tsx   /help   คู่มือ + UAT + PDF + ติดต่อ
```

`app/page.tsx` เดิมถูกลบ เนื้อหาย้ายเข้ากลุ่มใหม่ URL ยังเป็น `/` เหมือนเดิมเพราะ
วงเล็บใน Next.js ไม่เข้าไปอยู่ในเส้นทาง

`middleware.ts` **ไม่ต้องแก้** — `matcher` เป็นรายการเจาะจงที่ไม่ครอบ `/` และ
`/help` อยู่แล้ว การเปิดหน้าสาธารณะโดยไม่แตะตัวคุ้มกันคือการเปลี่ยนแปลงที่ปลอดภัยที่สุด
ที่ทำได้

### เลิกเด้งผู้ใช้ที่ล็อกอินแล้ว

`app/page.tsx` เดิม `redirect('/dashboard')` เมื่อมี session ทำให้เจ้าของระบบดู
หน้าแนะนำของตัวเองไม่ได้ พฤติกรรมใหม่คือแสดงหน้าแนะนำเสมอ และเปลี่ยนปุ่มบน nav
จาก "เข้าสู่ระบบ" เป็น "ไปที่ Dashboard" เมื่อมี session

### ไฟล์นิ่ง

สร้างโฟลเดอร์ `public/` (ยังไม่มีในโปรเจกต์) เก็บ `skouth-uat.pdf` — Next.js เสิร์ฟ
ไฟล์ในนี้ตรงจาก CDN ไม่ผ่านโค้ดฝั่งเซิร์ฟเวอร์ จึงไม่มีต้นทุน runtime และไม่ใช้โควตาใด

### ค่าคงที่

```
lib/help/contact.ts    อีเมลกลางองค์กร — แก้จุดเดียว
lib/help/docMeta.ts    { version, updatedAt } ของเอกสาร
lib/public/cta.ts      ข้อความและปลายทางของปุ่มหลักบนหน้าแรก
```

`cta.ts` แยกออกมาเพราะปุ่มนี้จะเปลี่ยนแน่นอนเมื่องานจำกัดโดเมนเสร็จ (ดูหัวข้อ
"งานถัดไป") ตอนนี้คือ "ดูคู่มือและติดต่อเรา" ไป `/help` ภายหลังจะเป็น
"สมัครด้วยอีเมลองค์กร" ไป `/signup` — การเก็บไว้จุดเดียวทำให้สลับได้โดยไม่ต้องรื้อหน้า

## เนื้อหาหน้าแรก

หกบล็อกเรียงลงมา ใช้ token สีและคลาสจาก `app/globals.css` ที่มีอยู่ ไม่สร้างระบบ
ดีไซน์ใหม่

1. **Hero** — พาดหัว คำอธิบายหนึ่งบรรทัด ภาพช่องค้นหาจำลองที่มีประโยคภาษาไทย
   และปุ่มเดียวคือ "ดูคู่มือและติดต่อเรา" ไป `/help`
   ช่องค้นหาเป็นภาพนิ่ง ไม่ใช่ input ที่กดได้ เพราะกดแล้วต้องล็อกอินอยู่ดี
2. **ทำไมถึงยาก** — สามประโยคสั้นเรื่องความยากของการหาคนไทยที่จบต่างประเทศ
3. **ฟีเจอร์หลักสี่บล็อก** — ค้นหาด้วยภาษาธรรมชาติ · คะแนนพร้อมเหตุผลภาษาไทย ·
   จับคู่กับตำแหน่งงาน · อัปเดตข้อมูลอัตโนมัติพร้อมคิวตรวจ
4. **PDPA** — วางเป็นจุดขาย ไม่ใช่หมายเหตุท้ายหน้า อ้างของที่มีจริงคือรายชื่อระงับ
   บันทึกกิจกรรม และการแยกตาราง `self_profiles` ออกจากฐานผู้สมัคร
5. **footer** เบา

ไม่มีบล็อกชวนติดต่อท้ายหน้า — ย้ายไปรวมที่ `/help` ตามที่เจ้าของงานกำหนด

## เนื้อหาหน้า `/help`

หน้าเดียวยาว มีสารบัญเกาะไว้กระโดด สี่ส่วนเรียงลงมา

1. **ดาวน์โหลดเอกสาร** — ปุ่ม "ดาวน์โหลด PDF" และ "เปิดในแท็บใหม่" พร้อมเวอร์ชัน
   และวันที่จาก `docMeta`
2. **คู่มือการใช้งาน** — เรียงตามหน้าจริงในระบบ: เข้าสู่ระบบและสมัคร → Dashboard →
   ค้นหา → หน้าผู้สมัคร → Shortlist → ตำแหน่งงาน → ประเมินตัวเอง → จัดการข้อมูล
   (เฉพาะ data_manager) → ตั้งค่า
3. **ตารางทดสอบการยอมรับ** — รหัสเคส ขั้นตอน ผลที่คาดหวัง ช่องผ่าน/ไม่ผ่าน หมายเหตุ
   ครอบคลุม **ทุกการทดสอบ** ตามที่เจ้าของงานกำหนด ไม่ใช่เฉพาะเส้นทางหลัก
   รวมเคสสิทธิ์ที่ member ต้องเข้าไม่ได้ และเคสที่บริการภายนอกล่ม
4. **ติดต่อเรา** — อีเมลกลางองค์กรจาก `contact.ts`

## เนื้อหาเอกสาร PDF

โครงเดียวกับหน้าเว็บ บวกหน้าปกที่มีชื่อระบบ เวอร์ชัน วันที่ และช่องให้ผู้ทดสอบ
ลงชื่อ

**ต้องฝังฟอนต์ไทย** — ไลบรารีสร้าง PDF ส่วนใหญ่ไม่มีฟอนต์ไทยมาให้ ถ้าไม่ฝัง
Sarabun หรือ Noto Sans Thai ตัวอักษรไทยจะกลายเป็นสี่เหลี่ยมเปล่าทั้งฉบับ

**ต้องสร้างไฟล์บนเครื่อง Windows ไม่ใช่ใน sandbox** — ตรวจแล้วว่า sandbox ไม่มี
ฟอนต์ไทยติดตั้งอยู่เลย และเข้าถึง PyPI กับ apt ไม่ได้ (proxy คืน 403) จึงติดตั้ง
ฟอนต์เพิ่มไม่ได้ ส่วน Windows มีฟอนต์ไทยมาให้อยู่แล้ว (Leelawadee UI, Tahoma)
ข้อจำกัดนี้เข้าทางการตัดสินใจที่ให้ดูแล PDF แยกจากหน้าเว็บอยู่แล้ว

แหล่งเนื้อหาสำหรับแปลงเป็น PDF อยู่ที่ `docs/uat/skouth-uat.md` — ไม่ใช่แหล่งเดียว
กับหน้าเว็บ (หน้าเว็บเขียนแยกตามที่ตัดสินใจไว้) แต่เป็นต้นฉบับที่เอาไปแปลงเป็น PDF
ได้โดยไม่ต้องพิมพ์ใหม่

## การทดสอบ

หน้าเหล่านี้เป็น JSX นิ่งเกือบทั้งหมด เทสต์ที่ยืนยันว่า "ข้อความนี้อยู่บนหน้า" ไม่ได้
ป้องกันอะไรและจะกลายเป็นภาระตอนแก้ถ้อยคำ จึงเขียนเฉพาะสองข้อที่ดักความล้มเหลวจริง

- **`public/skouth-uat.pdf` มีอยู่และขนาดมากกว่าศูนย์** ดักการลืม commit ไฟล์ ซึ่งทำให้
  ปุ่มดาวน์โหลด 404 บนโปรดักชันทั้งที่บนเครื่องตัวเองยังใช้ได้
- **ค่าคงที่ติดต่อไม่ใช่ placeholder** ดักการ deploy ทั้งที่ยังไม่ได้ใส่อีเมลจริง

ทั้งสองเป็น unit test ไม่แตะเครือข่าย จึงอยู่ในชุด `npm test` ที่ต้องเขียวเสมอ

ส่วนหน้าตาและความถูกต้องของเนื้อหาตรวจด้วยมือ — เขียนขั้นตอนไว้ใน
`docs/manual-tests/public-pages.md`

## ไฟล์ที่แตะ

สร้างใหม่

```
app/(public)/layout.tsx
app/(public)/page.tsx
app/(public)/help/page.tsx
lib/help/contact.ts
lib/help/docMeta.ts
lib/help/docAssets.test.ts       ตรวจว่า PDF มีอยู่จริง และอีเมลไม่ใช่ placeholder
public/skouth-uat.pdf
docs/manual-tests/public-pages.md
```

**ห้ามวางไฟล์เทสต์ไว้ใน `public/`** — Next.js เสิร์ฟทุกอย่างในโฟลเดอร์นั้นเป็นไฟล์
สาธารณะตรงจาก CDN ไฟล์ `.test.ts` ที่วางไว้ในนั้นจะกลายเป็นไฟล์ที่ใครก็ดาวน์โหลดได้
เทสต์จึงอยู่ที่ `lib/help/` แล้วอ่านไฟล์ใน `public/` ด้วย path แทน

แก้

```
app/page.tsx                     ลบ (ย้ายเข้า (public))
app/(app)/layout.tsx             เพิ่มลิงก์ "คู่มือ" ใน nav
app/globals.css                  คลาสสำหรับหน้าสาธารณะ
CLAUDE.md                        บันทึกว่าเนื้อหาสองชุดต้องแก้พร้อมกัน
```

ไม่แตะ — `middleware.ts` ทุกไฟล์ในกลุ่ม `(auth)` และตารางฐานข้อมูลทั้งหมด

## ความเสี่ยงที่รับไว้

**เนื้อหาสองชุดจะไม่ตรงกันในที่สุด** เป็นผลจากการเลือกที่ตั้งใจ ลดผลด้วยการประทับ
เวอร์ชันให้มองเห็น และบันทึกเตือนไว้ใน CLAUDE.md ว่าแก้คู่มือต้องแก้ทั้งสองที่

**หน้าแรกโฆษณาฟีเจอร์ที่ใช้งานจริงไม่ได้ในขณะนี้** — คะแนนเชิงลึกด้วย AI ต้องใช้
Gemini ที่ตอนนี้ถูกจำกัดความจุจนใช้ไม่ได้ ยอมรับได้เพราะคนนอกกดลองไม่ได้อยู่แล้ว
แต่ถ้าจะสาธิตสดต้องเปิด billing ก่อน

## งานถัดไป — จำกัดการสมัครตามโดเมนอีเมล

**ไม่อยู่ในขอบเขตของสเปคนี้** แต่บันทึกไว้เพราะจะเปลี่ยนถ้อยคำของปุ่มหลัก และเพราะ
ผลการค้นข้อมูลไม่ควรหายไป

โมเดลที่ต้องการคือแบบเดียวกับอีเมลที่มหาวิทยาลัยให้นักศึกษา — คนในองค์กรสมัครเองได้
คนนอกสมัครไม่ได้

**การลบหน้า `/signup` กันอะไรไม่ได้** เพราะ anon key เป็นค่าสาธารณะ ใครก็ยิง
`POST /auth/v1/signup` ตรงได้ จุดบังคับที่ข้ามไม่ได้คือ **Before User Created Hook**
ของ Supabase ซึ่งทำงานก่อนเขียนผู้ใช้ลงฐานข้อมูล เขียนเป็น Postgres function ได้เลย
โดยไม่ต้องมีบริการแยก และคืน error object เพื่อปฏิเสธการสมัคร
https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook

**ข้อจำกัดที่ต้องคิดพร้อมกัน** — การจำกัดโดเมนทำให้ประตูหน้าแคบลง แต่ห้องข้างในเท่าเดิม
ตอนนี้ `member` ค้นหาผู้สมัครได้ทั้งฐาน ถ้าองค์กรมีคนหลักร้อย การให้ทุกคนที่มีอีเมล
องค์กรเห็นข้อมูลส่วนบุคคลของคนที่ scrape มาทั้งหมดอาจกว้างเกินไปในแง่ PDPA
คำถามว่า `member` ควรเห็นอะไร เป็นคนละเรื่องกับการสมัคร และควรตอบพร้อมกัน
