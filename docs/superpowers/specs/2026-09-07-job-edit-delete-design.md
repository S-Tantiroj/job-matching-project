# v6 — แก้ไขและลบตำแหน่งงาน

**เป้าหมาย:** เปิดให้แก้ไขและลบงานที่สร้างไว้แล้ว โดยไม่ทำให้ embedding ของงาน
ค้างอยู่กับข้อความเก่า และไม่ทิ้งคะแนน AI กำพร้าไว้ในฐานข้อมูล

**สถาปัตยกรรมโดยรวม:** เพิ่มคอลัมน์ `analyses.job_id` พร้อม FK แบบ cascade เพื่อให้
ตอบได้ว่าแถวคะแนนไหนเป็นของงานไหน จากนั้นเพิ่ม `PATCH` และ `DELETE` ที่
`/api/jobs/[id]` กั้นด้วย role `data_manager` ฝั่งหน้าเว็บใช้ฟอร์มตัวเดียวกับตอนสร้าง
โดยรับค่าเริ่มต้นเข้ามา

**Stack:** ไม่มี dependency ใหม่ · migration หนึ่งไฟล์ (เพิ่มอย่างเดียว) · ไม่แตะ
ตาราง `jobs`

## ปัญหา

ตอนนี้สร้างงานได้อย่างเดียว พิมพ์ผิดแล้วแก้ไม่ได้ สร้างซ้ำแล้วลบไม่ได้ แต่การเพิ่ม
ปุ่มสองปุ่มไม่ใช่คำตอบ เพราะมีสามอย่างที่พังเงียบถ้าไม่จัดการ

### 1. `embedding` จะค้างอยู่กับข้อความเก่า

`jobs.embedding` สร้างจาก `buildJobEmbedText` ตอน insert `matchCandidatesForJob`
ใช้เวกเตอร์นั้นยิงหาผู้สมัคร **แก้ชื่องานหรือรายละเอียดแล้วไม่คำนวณใหม่ = การจับคู่
ยังใช้ข้อความเดิมต่อไปโดยไม่มีอาการอะไรให้เห็น** ผู้ใช้เห็นว่าแก้สำเร็จ แล้วสงสัยว่า
ทำไมผลลัพธ์ไม่เปลี่ยน

### 2. `analyses` ไม่มีอะไรชี้กลับไปหางาน

`analyses` คีย์ด้วย `(candidate_id, requirement_hash)` โดย hash มาจาก
`requirementHash(buildJobRequirementText(job))` ไม่มีคอลัมน์ `job_id` เลย ผลคือ:

- **แก้งานหนึ่งครั้ง คะแนนเชิงลึกที่ cache ไว้ทั้งหมดของงานนั้นเข้าไม่ถึงอีก** — hash
  เปลี่ยน แถวเก่ายังอยู่แต่ไม่มีทางค้นเจอ กดดูคะแนนใหม่คือจ่ายค่า Gemini ใหม่ทุกคน
- **ลบงานแล้วแถวเหล่านั้นค้างถาวร** ไม่มี FK ให้ cascade และไม่มีอะไรชี้กลับไปหางาน
  ที่ถูกลบ จึงไม่มีทางกวาดทีหลัง

### 3. `POST /api/jobs` ไม่มีประตู role

มีแค่ `getSession()` — `member` คนไหนก็สร้างงานได้ ต่างจาก `/api/ingest` ที่บังคับ
`data_manager` ถ้าเพิ่ม `DELETE` ตามรูปแบบเดิม ใครก็ลบงานได้

### สิ่งที่ **ไม่** เป็นปัญหา (ต่างจากกรณี `candidates`)

CLAUDE.md บันทึกไว้ว่าฟีเจอร์แก้ไขผู้สมัครถูกถอดออกเพราะรอบ sync ถัดไปจะเขียนทับ
ค่าที่แก้ด้วยมือ **กรณีนี้ไม่เหมือนกัน** — งานที่สร้างจากหน้าเว็บได้ `source: 'manual'`
และ `external_id: null` ส่วน `scripts/seed-jobs.ts` upsert บน `(source, external_id)`
ด้วย `source: 'synthetic'` เท่านั้น รันสคริปต์ซ้ำกี่ครั้งก็ไม่แตะงานที่ผู้ใช้สร้างเอง

ความเสี่ยงเหลือเฉพาะสี่งานที่มาจาก seed ซึ่งจัดการด้วยแถบเตือน ไม่ใช่การห้าม

## Migration 018

```sql
alter table public.analyses
  add column job_id uuid references public.jobs(id) on delete cascade;

create index analyses_job_id_idx on public.analyses (job_id);
```

**nullable โดยตั้งใจ** — การให้คะแนนจากหน้าผู้สมัคร (`/api/analyze`) ไม่มีงานผูกอยู่
และหน้าประเมินตัวเองใช้ `requirementHash` ตรงๆ ไม่ผ่าน `scoreCandidateAgainst`

**แถวที่มีอยู่แล้วจะเป็น NULL ตลอดไป** กวาดย้อนหลังไม่ได้เพราะไม่รู้ว่าแถวไหนเคยเป็น
ของงานไหน ยอมรับข้อจำกัดนี้ — ทางเลือกที่ไม่ใช้ migration ก็กวาดไม่ได้เหมือนกัน
และยังกวาดฉบับก่อนหน้าของงานที่ยังอยู่ไม่ได้ด้วย

**ข้อจำกัดที่ migration นี้ไม่ได้แก้:** ถ้าสองงานมีข้อความความต้องการเหมือนกันเป๊ะ
มันใช้แถว `analyses` ร่วมกันแถวเดียว (`unique (candidate_id, requirement_hash)`)
แล้ว `job_id` ชี้ไปที่งานที่ให้คะแนนก่อน ลบงานนั้นแล้ว cache ของอีกงานหายไปด้วย
เป็นข้อจำกัดของการ cache ด้วย hash ของเนื้อหา ไม่ใช่ของ migration นี้

## ฟังก์ชันบริสุทธิ์สองตัว

เพิ่มใน `lib/jobs/normalize.ts`:

```ts
export function embedTextChanged(before: JobInput, after: JobInput): boolean
export function requirementTextChanged(before: JobInput, after: JobInput): boolean
```

เทียบผลของ `buildJobEmbedText` และ `buildJobRequirementText` ตรงๆ ใช้ทำสองอย่าง:

- **ข้ามการเรียก Gemini เมื่อข้อความ embedding ไม่เปลี่ยน** — แนวคิดเดียวกับ
  `embed_hash` ฝั่งผู้สมัคร แก้แล้วเปลี่ยนกลับเป็นค่าเดิมไม่ควรเสียเงิน
- **ไม่ขึ้นคำเตือนเรื่อง cache เมื่อข้อความความต้องการไม่เปลี่ยน**

**สองฟังก์ชันนี้ไม่ซ้ำซ้อนกัน** — `category` อยู่ใน `buildJobEmbedText` แต่ไม่อยู่ใน
`buildJobRequirementText` แก้หมวดงานจึงต้อง re-embed แต่ cache คะแนนยังใช้ได้
ใครที่คิดจะยุบสองตัวนี้เป็นตัวเดียวควรอ่านแถวนี้ก่อน

## `lib/jobs/update.ts`

```ts
updateJob(id: string, patch: Partial<JobInput>)
  -> { reembedded: boolean; staleScoresRemoved: number }

deleteJob(id: string) -> { deleted: boolean }
```

`updateJob` อ่านแถวเดิม → merge patch ทับ → ถ้า `embedTextChanged` จึงเรียก
`embedText` → update แถว **ต้องเช็ค `error` ของทุก `.from()`** ตามข้อบังคับใน
CLAUDE.md

**ถ้า `requirementTextChanged` ให้ลบ `analyses where job_id = id` ทิ้งด้วย** —
แถวเหล่านั้น hash ไม่ตรงกับข้อความใหม่แล้ว จึงไม่มีวันถูกอ่านอีก และเพราะ `job_id`
ยังชี้ไปที่งานที่ยังอยู่ มันจะไม่ถูก cascade กวาดตอนไหนเลย **ไม่ลบตอนนี้ = ทุกครั้ง
ที่แก้งานจะทิ้งขยะเพิ่มถาวร** ลบตอนแก้จึงเป็นเงื่อนไขที่ทำให้ "กวาดทิ้ง" ครบจริง
ไม่ใช่ครบเฉพาะตอนลบงาน

`staleScoresRemoved` คือจำนวนแถวที่ถูกลบ ใช้ยืนยันกับผู้ใช้หลังบันทึกว่าตรงกับที่
เตือนไว้ก่อนกด

`deleteJob` ลบแล้ว `.select('id')` เพื่อรู้ว่ามีแถวถูกลบจริงไหม (แยก "ลบสำเร็จ" ออกจาก
"ไม่มีงานนี้อยู่แล้ว") แถว `analyses` หายไปเองด้วย cascade — **ไม่มีโค้ดกวาดที่ต้อง
จำไปเรียก** ซึ่งเป็นเหตุผลหลักที่เลือกทาง migration

## Route

`app/api/jobs/[id]/route.ts` — `PATCH` และ `DELETE` ทั้งคู่:

```
getSession() -> null           => 401
hasRole(role, 'data_manager') ไม่ผ่าน => 403 พร้อมข้อความไทย
job ไม่มีอยู่                   => 404
```

**ประตูต้องอยู่ก่อนการทำงานทุกอย่าง** ไม่ใช่หลัง — ประตูที่อยู่หลัง `updateJob`
คืนสถานะถูกแต่ข้อมูลเปลี่ยนไปแล้ว

**PATCH ตัด `source` และ `external_id` ทิ้งจาก body** ทั้งสองเป็นข้อมูลที่มาของแถว
ไม่ใช่เนื้อหาที่แก้ได้ และการเปลี่ยน `external_id` อาจชนกับ unique constraint
`(source, external_id)` แล้วพังแบบอธิบายยาก **ตัดที่ route ไม่ใช่แค่ไม่แสดงในฟอร์ม**
เพราะ body มาจาก client ที่เชื่อไม่ได้

`POST /api/jobs` เพิ่มประตูเดียวกัน — **นี่คือการเปลี่ยนพฤติกรรมของของเดิม**
`member` ที่เคยสร้างงานได้จะสร้างไม่ได้อีกต่อไป

## หน้าจอ

**`CreateJobForm` → `JobForm`** รับ prop `job?: JobInput & { id: string; source: string }`
ไม่มี = โหมดสร้าง มี = โหมดแก้ ตามแบบเดียวกับที่ `ProfileForm` ใช้ทั้งตรวจ draft และกรอกเอง

**หน้าแก้อยู่ที่เส้นทางของตัวเอง** `app/(app)/jobs/[id]/edit/page.tsx` ไม่ใช่สลับโหมด
ในหน้าเดิม — หน้ารายละเอียดเป็น server component ส่วนฟอร์มเป็น client ถ้าสลับใน
หน้าเดียวต้องลากส่วนอ่านไปเป็น client ตามไปด้วย แยกเส้นทางแล้วได้ URL ที่กดย้อนกลับ
ได้ด้วย `matcher` ครอบอยู่แล้วผ่าน `/jobs/:path*`

**คำเตือนเรื่อง cache เป็นแบบสด** — หน้า edit นับ `analyses where job_id = ...`
ฝั่งเซิร์ฟเวอร์แล้วส่งตัวเลขเข้าฟอร์ม ฟอร์ม import `buildJobRequirementText` (ฟังก์ชัน
บริสุทธิ์ ใช้ใน client ได้) มาเทียบข้อความก่อน/หลังขณะพิมพ์ คำเตือนจึงโผล่เฉพาะตอนที่
การแก้นั้นทำให้ hash เปลี่ยนจริง ไม่ใช่ขึ้นตลอดจนคนเลิกอ่าน

**ปุ่มลบ** `DeleteJobButton` พร้อมกล่องยืนยัน ตามแบบ `DeleteCandidatesDialog`
ที่มีอยู่ ลบสำเร็จแล้ว `router.push('/jobs')`

**แถบเตือนงานที่มาจาก seed** — หน้ารายละเอียดต้อง `select` คอลัมน์ `source` เพิ่ม
(ตอนนี้ยังไม่ได้ดึง) ถ้า `source === 'synthetic'` ทั้งหน้า edit และกล่องลบขึ้นข้อความว่า
งานนี้มาจากสคริปต์ seed รัน `npx tsx scripts/seed-jobs.ts` อีกครั้งแล้วค่าที่แก้จะกลับคืน
**เตือนแต่ไม่ห้าม**

**ปุ่มแก้ไขและลบซ่อนจาก `member`** บนหน้ารายละเอียด — เป็นความสะอาดของหน้าจอ
ไม่ใช่ความปลอดภัย ประตูจริงอยู่ที่ route

## บั๊กพ่วงที่แก้ไปด้วย

ทั้งสองอยู่ในไฟล์ตระกูลเดียวกับที่งานนี้แก้อยู่แล้ว และผิดข้อบังคับใน CLAUDE.md
ที่ว่า `.rpc()` และ `.from()` ต้องเช็ค `error` เสมอ

- **`upsertJob`** ไม่เช็ค `error` แล้วอ่าน `(data as any).id` ต่อทันที — insert พังเมื่อไร
  จะได้ `TypeError: Cannot read properties of null` แทนข้อความที่บอกว่าเกิดอะไรขึ้น
- **`matchCandidatesForJob`** ไม่เช็ค `error` ทั้ง `.rpc()` และ `.from()` — RPC พังแล้ว
  หน้า job จะขึ้นว่า "ไม่มีผู้สมัครเข้าเกณฑ์" แทนที่จะบอกว่าพัง อาการเดียวกับที่หน้าค้นหา
  เคยเป็นเมื่อ 2026-09-07 และใช้เวลาไล่หาสาเหตุนาน

## ทางเลือกที่ตัดออก

**ใช้ `requirement_hash` อย่างเดียว ไม่แตะฐานข้อมูล** — คำนวณ hash จากงานฉบับ
ปัจจุบันแล้วใช้นับและลบ ไม่ต้องมี migration **ตัดออกเพราะ** แถวจากฉบับก่อนหน้าที่
เคยแก้ไปแล้วหาไม่เจอ (ไม่เก็บข้อความเก่าไว้) แก้งานสามครั้งแล้วลบจะกวาดได้แค่ฉบับ
ที่สาม การ "กวาดทิ้ง" จึงถูกแค่บางส่วน และต้องมีโค้ดกวาดที่ต้องจำไปเรียกทุกจุดที่ลบงาน
แทนที่จะให้ Postgres ทำให้

**ลบแบบซ่อนไว้ (archived)** — กู้คืนได้ แต่ต้องเพิ่มคอลัมน์แล้วไล่แก้ทุกที่ที่ query
`jobs` (หน้ารายการ, `match_jobs` RPC, `seed-jobs.ts`) ลืมที่เดียวแล้วงานที่ "ลบแล้ว"
จะโผล่กลับมาในบางหน้า ตัดสินใจเลือกลบจริง

**ห้ามแก้งานที่มาจาก seed** — ตัดออก เลือกเตือนแทน คนที่รู้ว่าตัวเองทำอะไรอยู่ควร
แก้ได้ และการห้ามไม่ได้ป้องกันอะไรที่การเตือนป้องกันไม่ได้

**ให้แก้ได้เฉพาะฟิลด์ที่ไม่กระทบ cache** — พิจารณาแล้วไม่เอา ฟิลด์ที่แก้ได้จะเหลือแค่
`company` กับ `location` ซึ่งทั้งคู่ก็อยู่ใน `buildJobRequirementText` อยู่ดี ไม่เหลืออะไร

## สิ่งที่ยอมทิ้ง

**ไม่มีประวัติการแก้ไข** — แก้แล้วค่าเดิมหายไปเลย ไม่รู้ว่าใครแก้อะไรเมื่อไร
ตาราง `activity_log` มีอยู่แล้วและรองรับ `entity_type` แต่ยังไม่มีค่า `'job'` การเพิ่ม
เป็นงานคนละก้อน

**ลบแล้วกู้คืนไม่ได้** กล่องยืนยันคือด่านเดียว

**แถว `analyses` ที่ `job_id` เป็น NULL กวาดไม่ได้** ทั้งของเก่าก่อน migration และ
ของฉบับก่อนหน้าที่เคยแก้ไปแล้วก่อนวันที่ทำฟีเจอร์นี้
